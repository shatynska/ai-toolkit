## Context

`skills/testing` shipped with a pointer section naming four skills as where stack-specific testing material belongs, and with an explicit acknowledgement that those targets were thin. `add-testing-skill`'s own risk register recorded it: "the pointer section directs readers to skills that currently say nothing about testing… on day one the pointer is a promissory note." This change pays two of the four notes. See proposal.md for motivation; this document covers how the two skills are shaped.

Both target skills already pre-split into `SKILL.md` plus `references/`, and both capabilities carry a *Structure Separates the Always-Resident Floor from On-Demand Depth* requirement fixing that shape. So the structural question is not whether to split but where each piece of new content sits relative to a split that already exists — which is a narrower and better-constrained question than the one `add-testing-skill` faced.

## Goals / Non-Goals

**Goals:**
- Make the `testing` pointer resolve to real content for the two stacks the motivating project uses.
- Keep the division of labour intact: the floor states what makes evidence interpretable, the language skill states how to express it, and neither restates the other.
- Answer the question that is actually hard in LangGraph testing — stubbing a model that emits tool calls — rather than the questions that are easy.
- Hold both additions to the verification discipline their own capabilities already require.

**Non-Goals:**
- Teaching `pytest` or LangGraph testing to a human. Both skills load into an agent's context.
- Testing runners other than `pytest`. The cold-run observation quoted in proposal.md named `unittest`; `python-practice`'s consuming-project deference is the route for a project on a different runner, and the reference states its own runner scope. Recorded here so the decision is visible from this document, not only from the proposal.
- A testing tutorial. The same trap-first bar the existing content meets applies: material a competent model already supplies unprompted does not earn a place.
- Coverage policy, test-suite architecture, or CI shape — excluded by `skills/testing`'s Non-Goals and not reintroduced here through a side door.
- `bash` and `terraform` testing sections, which the `testing` pointer also promises. Same shape of work, different stacks, separate verification burden — see Decision 6.
- Any edit to `skills/testing`'s **guidance content**, whose pointer already anticipates this content. Its recorded fixtures are excluded from this non-goal: `skill-authoring` forbids deferring a fixture this change falsifies, so repairing one is in scope even though it edits that file.

## Decisions

**1. Both skills get a `references/testing.md`; neither gets a large floor addition.**
The alternative — putting testing content in each `SKILL.md` — fails the budget both capabilities already enforce. `python`'s floor is 1,532 words carrying five trap sections; `langgraph`'s is 1,034 words carrying six. Testing content substantial enough to be useful would roughly double either, and both capabilities have a scenario requiring that deep material not load on a trigger that does not concern it. A reference file is what both skills already use for exactly this, so this decision follows their shape rather than introducing one.

**2. `langgraph`'s floor gains the test-level distinction, and only that.**
`langgraph-practice` requires testing guidance in the always-resident floor — it is named in the structure requirement's minimum list — so unlike `python`, this skill cannot route everything to a reference. What earns floor space is the distinction that changes what an agent *does* before it writes anything, and it is a **four-rung ladder rather than three**: a node's behavior is testable by calling the node; a routing *decision* is testable by calling whatever makes it — the path function where the edge is conditional, or the node itself where routing is a `Command(goto=...)` return, since that form has no path function at all — calling the *node* does not exercise the edge, but that is a fact about the node, not evidence that the decision needs a graph; that the decision *reaches the intended node* does need the compiled graph; and cross-turn behavior needs a checkpointer. An earlier draft of this decision compressed the middle two rungs into "routing is not [testable as a plain function]", which is false and, worse, pushes a test above the smallest unit that can observe the behavior — the exact rule `testing-practice` states and this change cross-references. That is orientation, not construction. How to build each — especially the model stub — is depth and routes to the reference. The floor grows by roughly a paragraph rather than a section.

**3. The hard part is named as the hard part.**
Most LangGraph testing guidance in the wild stops at "mock the LLM." That is the easy half. A stub returning plain text cannot exercise a tool-calling branch at all: the graph routes on whether the model *requested a tool*, and a text-only response never does, so the branch under test silently never runs and the test passes having established nothing — which is `skills/testing`'s fourth failure state reached through a LangGraph-specific mechanism. The reference therefore leads with attaching tool calls to a stubbed response, and the delta spec makes that a requirement rather than leaving it to the author's sense of proportion.

**4. Cross-references point both ways, correcting a one-directional precedent.**
`add-testing-skill` recorded that `python`'s cross-reference to `langgraph` is one-directional and that this was copied as a shape rather than cited as a mutual convention. Here both new references point back to `skills/testing` for the general discipline, and both delta specs make *that* a requirement with a scenario. Note precisely what those scenarios bind: they forbid the reference file from **restating** the floor's material. The floor-level pointer — a line in each `SKILL.md` naming `skills/testing` so a reader entering through the language skill discovers the floor at all — is tasked at 4.4 and deliberately left unspecified, because it is a discoverability convenience rather than a behavior the capability needs to guarantee. Recorded so a later reader does not mistake the tasked edit for a specified requirement. The reason is drift: a reader who enters through `python` on a test-writing task would otherwise never learn the floor exists, and would be free to restate its rules locally — which is the exact duplication the adapter design across this library is built to avoid.

**5. Verification requires installing two packages, and that is a prerequisite rather than a nicety.**
`python-practice` requires version-dependent claims verified against a live interpreter and tooling; `langgraph-practice` requires API claims verified against the released package. Neither `pytest` nor `langgraph` is installed here. The claims most at risk are exactly the ones worth writing: what `pytest` rewrites in a bare `assert`, whether `-O` strips assertions, and — for LangGraph — the concrete mechanism by which a stubbed response carries tool calls, which is where a plausible-sounding but wrong API would do the most damage. `add-langgraph-skill` installed to a `--target` directory rather than a venv in this environment and that route is available again. Where a live check proves impossible, the claim is sourced from current documentation and recorded as resting on documentation, which `langgraph-practice` explicitly permits.

**5a. The compile-vs-execution claim is verified in both directions, not confirmed in one.**
The floor states that a bad routing destination surfaces at execution rather than at `.compile()`. That is true when the graph cannot know the destinations in advance, and may be false when it can — an explicit `path_map`, or a path function with an annotated return type, gives the graph the destination set at definition time. A verification worded to *confirm* the claim passes on the no-`path_map` case and never reaches the exception, which is how an unconditional falsehood ships as a checked fact. Task 1.4 therefore verifies both constructions explicitly.

This has a consequence beyond this change: `skills/langgraph/SKILL.md` already carries the unconditional form, and `langgraph-practice`'s *Conditional-Edge Routing and Recursion Limits Are Covered* — which this change does **not** modify — states it too. That requirement is therefore **added to this change's `MODIFIED` set**, as a fourth modified requirement. Deferring it was considered and rejected: this delta already binds the floor *normatively* to the qualified form, so the conflict is created by this change's own text regardless of what verification returns — leaving the correction contingent would ship an archived spec whose two requirements demand contradictory statements from the same always-resident section. Task 1.6 accordingly verifies the claim and reports, rather than deciding whether to correct.

**6. `bash` and `terraform` are deferred, and the deferral is recorded rather than silent.**
The `testing` pointer names four skills. Doing two leaves two promissory notes outstanding, which is worse than doing none only if the remaining two are forgotten. They are deferred for a stated reason — different stacks, different verification (ShellCheck's interaction with test scripts; `terraform test`'s own harness), and no motivating project driving them — and this decision is where a later reader finds that it was a choice.

**7. This is the repository's first change carrying `MODIFIED` deltas, and that is a risk, not a formality.**
Four requirements are modified across two capabilities. The `MODIFIED` path has two failure modes this repository has never exercised: a header that does not match an existing requirement exactly is silently treated as an addition, and a partial `MODIFIED` body loses the omitted detail at archive time. Both delta files therefore carry the complete current text of each modified requirement with the additions folded in, not a diff, and each header is verified by direct comparison against `specsRoot` rather than by trusting a validator that cannot see the failure.

One deliberate substitution is recorded rather than left to be discovered, since detail-loss under `MODIFIED` is this decision's own named risk: `langgraph-practice`'s scenario *The floor points to where the depth lives* previously named `references/checkpointing.md` and `references/multi-agent-tool-calling.md` explicitly in its `THEN`, and now generalises to "each `references/` file" because a third file exists. The file-level precision is not lost — all three names move into the requirement's body, where they bind more strongly than a scenario's illustrative list did.

## Risks / Trade-offs

- **A `MODIFIED` delta that silently becomes an `ADDED` one.** A header mismatch does not error; it produces a duplicate requirement in the main spec at archive time. → *Mitigation*: each `MODIFIED` header was compared **character-for-character against the requirement it names in `specsRoot`**, which is the only thing that establishes a match. An earlier draft of this mitigation credited `openspec validate` passing — that is void reasoning, since this very decision states a mismatch is *silent*, so a passing validation establishes nothing about the headers. Re-verified at archive, per task 7.1.
- **Verification may be blocked.** This environment has resisted `venv` before, and a `--target` install pollutes an import path that later steps depend on. → *Mitigation*: the fallback is documented-source claims, explicitly recorded as such — `langgraph-practice` permits it and requires the provenance be stated, so the failure mode is a weaker claim honestly labelled rather than an unverified one presented as checked.
- **The LangGraph stubbing API is the most likely thing to be wrong.** It is the content with the highest value and the highest chance of a plausible-but-wrong answer, and `add-langgraph-skill` already found one such assumption false (supervisor/swarm helpers that do not exist in the core package). → *Mitigation*: it is the first claim verified, and if it cannot be verified live the reference says so at the point of the claim rather than in a footnote.
- **Two skills' descriptions change, invalidating their recorded trigger checks.** → *Mitigation*: both are re-run and updated within this change; `skill-authoring` requires exactly this and forbids deferring it.
- **Scope creep toward a testing tutorial.** Testing has more surface than a trap list, and it is easy to keep writing. → *Mitigation*: the same bar the existing content meets — a rule earns a place only if it changes what an agent does — applied at draft, with what was cut recorded.
