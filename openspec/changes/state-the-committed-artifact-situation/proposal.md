## Why

`testing`'s enumeration of the situations a test-writing task arrives in is exhaustive by construction — the target exists, or it does not — and one kind of suite falls outside what either reading covers.

Where an assertion does not execute the behaviour it asserts — a static read of a committed file, of the source of a program it never calls, or of a module imported only so a constant can be read out of it — the target is present whatever the check does. Where that target already carries the asserted property, a pass establishes nothing: the same test passes identically against a check that reads nothing at all. The skill's second situation says a pass there "establishes that the code currently behaves as asserted", which is true of code and false of a committed artifact, and its fourth failure state — the alarm — is keyed to "before any implementation existed", so it never fires. A whole suite can be green and assert nothing, with no stated rule broken.

**The escape is a synthetic fixture, and projects find it — expensively, once per change, under no name.** In `infrastructure`, `.github/tests` is exactly such a suite. Thirteen classes in one module there pair a check with a discriminator that runs it over a fixture tree, and one of them says why in its own docstring: *"The class above would pass identically against a check that read nothing."* That is this skill's missing situation, re-derived from first principles. The pattern carries no name, so each author invents its shape and its size: `TestTheConventionsFileBindsTheSharedStateRuleToMolecule` is 71 lines and the discriminator beside it is 629. Across that module the paired classes hold 3,873 of 11,413 lines in classes — 34%.

**And nothing bounds how much of it a change owes.** `change-test-authoring` makes coverage a count: *"the number of scenarios in the delta specs equals the number accounted for in the manifest."* That is a floor with no ceiling, and no requirement in either capability supplies one. The observable result in `infrastructure` is a median of roughly 1,250 lines of test per change, six of the last nineteen `derive tests` commits above 1,400, and one at 2,950. A structural clone detection over all 481 functions in that suite attributes 4.3% to redundancy, so this is not duplication being counted twice — it is the discriminator layer, sized by an author with no stated target.

The two are one concern. The volume is the discriminator layer, the discriminator layer exists because the situation is unnamed, and an author who has just worked out for themselves why their suite needs one has no basis to stop.

## What Changes

- **`testing` states a third situation: the assertion does not execute the behaviour it asserts.** A pass establishes nothing there, and discrimination is reached by running the check over material the test supplies. The line between it and the second situation is what the assertion executes, not what kind of thing the target is and not whether the target was loaded — a shell script read without being run is in the third situation, so is a module imported only so a constant can be read out of it, and code the check calls is in the second. The two existing situations stay as they are; the fourth failure state gains the reading this situation gives it, the way the second and fourth already carry different readings across the first two.

- **`testing` scopes the obligation and names who discharges it.** It attaches to a check as authored or modified, so a suite predating the rule carries an undischarged obligation rather than a violation. And because a discriminator supplies its own material, it does not wait for the check to go green — it is written in the same pass, by the same author, beside a check that is still red. An obligation deferred to the moment a check goes green would be owed by nobody: nothing re-dispatches a test author then.

- **`testing` states what the mechanism's own negative result means.** A check that passes over material chosen to falsify it asserts nothing — the fourth failure state's second branch, reached deliberately rather than stumbled on — and is repaired or reported, never left standing as coverage. This is the finding the whole obligation exists to produce, and stating where the routing *ends* is what makes it a mechanism rather than a gesture.

- **`testing` states what an observed failure discharges, and what it does not.** A check written against a property its target does not yet carry is red at authoring and goes green as the change lands — the common case wherever tests precede the change they cover — and that transition establishes discrimination on real content. It is recorded, and the fixture is still owed once the check is green: the red run leaves nothing in the suite, so nothing re-establishes the property afterwards and a later edit can stop the check asserting with no result changing. Stating the obligation on the check's steady state rather than on when it was written is what keeps it binding — where tests are derived before implementation every check is red at authoring, so an exemption for that case would exempt every check in such a project.

- **`testing` states what a discriminator is for, which is what bounds it.** Its job is to establish that the check can fail — to falsify it once, on the property the check exists to assert. It is not an enumeration of the check's input space, and a case added because it is expressible rather than because it discriminates is recorded as derived like any other invented assertion. This bounds by disclosure rather than by prohibition: it forbids no case and trims nothing already written, and what it adds is that an author who cannot say what a case falsifies has to label it. That is what the count rule has no counterpart to — a reviewable question about a body of tests nobody currently classifies, because the whole layer reads as methodology rather than as assertion.

## Non-Goals

- **Carrying any of this into `change-test-authoring`'s manifest.** The first six drafts of this change did, and the manifest half generated six of the last nine blocking findings across the review loop while growing from one line to four obligations, a repeat-pass carry-forward, a conditioned fallback and a needed amendment to the dispatch contract — reaching exactly the neighbouring requirements it was scoped to avoid. It is deferred whole, with the review's findings as its starting evidence, and is recorded in `docs/change-queue.md`. The floor states the obligations; where a project records them is the floor's existing recording-surface rule until a change settles it for this agent.

- **Shared test arrangement — a suite's fixture builders, where they live, and when a new bespoke one is warranted.** It is the other half of the volume problem and it is larger than this change: `infrastructure` spends 2,259 lines on inline synthetic fixture text across 23 `mkdtemp` sites, and `commerce-ops` has already built the answer — a `tests/support/` package 241 of its 371 test files import, and twenty standing rules governing it. Promoting that body needs a bundled reference and touches the agent's additive-only guarantee, which this change does not. Recorded in `docs/change-queue.md`.

- **Whether a project should have such a suite at all.** `terraform` and `ansible` already leave harness adoption to the project's own scale, and nothing here changes that. This change binds a suite that exists.

- **Restating the situation in the language skills.** The situation is language-independent — it turns on what the target is, not on what reads it — so it belongs in the floor, and the routing requirement already sends machinery questions downward.

## Capabilities

MODIFIED alongside it: the failure states, whose fourth gains the reading the third situation gives it; and the specified/derived/untested classification, which gains what a discriminator is for and nothing else — its existing paragraphs and scenarios are carried through verbatim.

## Impact

- Changed, among library assets: `skills/testing/SKILL.md` only — the situations section, the failure-states section (its introducing paragraph, the third state's two-way phrase, and the fourth state's third-situation reading), and the classification section. No agent, no rule fragment, no language skill.
- No new file, no bundled reference, no change to any language skill.
- `docs/change-queue.md` is corrected where this change's artifacts settled something its entries state differently (tasks 5.1 and 5.2); it is not a library asset, which is why the line above is scoped to those. It carries **two** entries this change relies on: the shared-arrangement one, and `record-the-discriminator-obligation-in-the-manifest`, which holds the deferred manifest work together with the review findings that established it is not a one-requirement change. It was written while this change was being drafted rather than at its end, and outside the change, so that it survives this change being abandoned.
- **This repository's own `tests/cases/` falls under the new requirement** and is not brought into conformance here. Ten of its cases guard against a vacuous pass in their own words, each of them reading a committed library file to do it; the requirement scopes itself to a check as authored or modified, so those cases carry an undischarged obligation rather than a violation and no retrofit is owed. That scope is in the delta itself, not in `design.md`'s non-binding section, whose quantity, fixture-location and trimming clauses would not have covered a green check with no discriminator at all, and whose clause on a suite predating the rule describes that case rather than binding it. Named because a change stating a rule its own tree does not yet meet should say so.
