## 3. Write the Agent

- [ ] 3.1 Create `agents/openspec-test-writer.md` with the frontmatter approved at 2.6 and an opening that establishes the fresh-context stance: it holds no history, the conversation that produced the change is not its own, and it knows only what the dispatch names.
- [ ] 3.2 Write the dispatch contract section: the essential inputs (change name, absolute `changeRoot`, resolved artifact paths, absolute `.openspec.yaml` path, the project's convention-file paths or their stated absence, test command, test-path glob), plus **`specsRoot` as conditionally essential** — required where the change carries a `MODIFIED`, `REMOVED` or `RENAMED` delta, and explicitly *not* blocking where every delta is `ADDED`; plus the **optional** absolute path of an earlier `test-manifest.md`, whose absence changes what the obsolete search can draw on but never whether the pass proceeds, the instruction not to search for a change or infer the repository, absolute-path discipline, and blocked-and-stop when an essential input is missing.
- [ ] 3.3 Write the section directing that `ai-toolkit:testing` and the matching language or tool skill be loaded **before** any test is written, naming which skills may be loaded, per Decision 3. State that the coarse `Skill` grant is a norm rather than a mechanism rather than implying it is enforced.
- [ ] 3.3a Write the section discharging inherited project-convention obligations non-interactively, per design.md Decision 2's translation licence: read the dispatched convention files; record an unanswerable project question in the manifest with the assumption taken and the tests depending on it; surface it in the report; and never treat the absence of a channel as making the floor's obligation inapplicable.
- [ ] 3.3b Write the **read-bound** section, per design.md Decision 14: the agent reads only the change's artifacts at supplied paths, `specsRoot`, the dispatched convention files, a supplied prior manifest, and files within the test-path glob; it does not read the implementation of the behaviour under test, and establishes what a `MODIFIED` delta supersedes by comparing the delta with the existing requirement rather than by reading code; a read it cannot avoid is reported as a departure from the bound, not taken silently.
- [ ] 3.4 Write the scenario-enumeration section: every `#### Scenario:` in the delta specs is accounted for exactly once, covered or recorded as uncovered with a reason, and coverage is a count rather than a judgment. State that a scenario may need several tests and a test may serve several scenarios, so the mapping is many-to-many — per the risk recorded in design.md.
- [ ] 3.5 Write the delta-operations section: `ADDED` produces tests; **`MODIFIED` produces both** — new tests for the requirement's scenarios as revised, and obsolete-list entries for the tests bearing on the superseded behavior, identified by the stated procedure at 3.5a — because a delta operation is not a reason to leave changed behavior uncovered, and a new test is additive so it does not reopen the path to editing an existing one; `REMOVED` produces obsolete-list entries alone; neither ever produces an edit; `RENAMED` is recorded as a rename; and `skip_specs: true` is a file read — from the dispatched `.openspec.yaml` path — that stops the pass with a report that the existing suite must stay green. State that scenarios reached through a `REMOVED` or `RENAMED` delta are accounted for as uncovered-with-the-operation-as-reason, so the count reconciles across all four operations. State that absent delta specs **with** the marker routes to this exempt report and **without** it routes to blocked, so an exempt change is distinguishable from a malformed dispatch. Include that `specsRoot` is read to establish what a `MODIFIED` delta supersedes.
- [ ] 3.5a Write the **obsolete-entry identification** section, per design.md Decision 4: search only within the dispatched test-path glob, and use an earlier `test-manifest.md` as a scenario-to-test mapping **only where the dispatch supplies its absolute path**, never by locating one — the useful referent sits in an archived change directory, and constructing that path is what the dispatch contract forbids; record for every entry the runner-selectable identifier, the superseding delta, and the evidence it was matched on; mark every entry a candidate for human confirmation rather than a conclusion; and state explicitly when no bearing test was found, distinguishing that from asserting none exists. The list is the input to someone else's destructive action, so an entry made on invisible grounds relocates the loss rather than preventing it.
- [ ] 3.6 Write the additive-only section: never edit, delete, or disable an existing test under any delta operation or for any stated reason; never write outside the dispatch's test-path glob **except for the manifest at `<changeRoot>/test-manifest.md`**, which is the single enumerated exception, and treat any other outside write as a stop-and-report; state the bound on what counts as a write — this binds writes **the agent performs**, and files produced as a side effect of running the dispatched test command (caches, coverage output, compiled artifacts) are not the agent's writes and must not stop the pass, or the agent halts on its own runner's output on the ordinary path of taking a baseline; never write implementation, and report a target-absent failure rather than creating a stub. State the additive property as something a dispatcher can rely on without reading the agent's reasoning.
- [ ] 3.7 Write the manifest section: the exact path `<changeRoot>/test-manifest.md`, and its required contents — scenario-to-test mapping, uncovered scenarios with reasons, assertion classifications, the obsolete list with the superseding delta, unresolved project questions with their assumptions, obsolete entries each carrying their evidence and candidate marking, and the baseline in whichever form the testing floor permits — including a scoped baseline with its scope, without restating or narrowing that floor rule. Require test identifiers in a form the runner can select individually.
- [ ] 3.8 Write the report section. Record in design.md, or here, that this capability deliberately does **not** fix the report's structure normatively the way `change-review` does for the reviewer — the reviewer's verdict is consumed by a human deciding whether to proceed, while this report is consumed alongside a manifest that already carries the structured result. State that the manifest is not a schema artifact and is therefore not surfaced by `openspec instructions apply`, so it must be read deliberately.
