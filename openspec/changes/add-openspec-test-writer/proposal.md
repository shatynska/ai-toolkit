## Why

`skills/testing` states what makes a test's evidence interpretable, but nothing applies it inside the OpenSpec flow, and the flow is where the material is richest. A change's delta specs already enumerate test obligations in a fixed, countable form: every `#### Scenario:` is a WHEN/THEN pair, every requirement must carry at least one, and the schema's own instruction says scenarios "should be testable — each scenario is a potential test case". Today nothing turns that enumeration into tests, so whether a change's stated behavior is covered depends on whoever implements it remembering to look.

The sharper reason is one `add-testing-skill` recorded and deliberately deferred. When a single agent writes implementation and tests in one reasoning trace, the two share blind spots: a case it did not think of while coding is one it will not think of while testing. `testing`'s specified/derived split narrows that — an assertion must trace to a stated requirement rather than to the code as written — but it cannot close it, because closing it needs a test author that never sees the implementation. That author is this agent, and its design.md names it as the remedy the floor could not supply.

There is a third gap the floor cannot reach at all. `MODIFIED` and `REMOVED` deltas mean existing tests now assert superseded behavior. `testing` requires those be reported as superseded rather than quietly rewritten, but a floor loaded into whoever happens to be working cannot guarantee anyone looks for them. An agent reading the delta operations directly can.

## What Changes

- Add `agents/openspec-test-writer.md` — a subagent dispatched after a change is reviewed and before implementation begins. It reads the change's delta specs, turns every `#### Scenario:` into a test obligation, writes tests, records what it did in a manifest, and reports. It is an **OpenSpec adapter**, not a second copy of the testing standard.
- **Invoke `ai-toolkit:testing` rather than restating it.** The agent's `tools` grant includes `Skill`, and its body directs it to load `testing` — plus the matching language skill — before writing anything. Verified capability: a subagent declaring `Skill` sees the full skill listing and can invoke a plugin skill by namespaced name. The agent therefore carries only what is OpenSpec-specific; every rule about baselines, failure states, provenance, and never weakening a test stays in the skill that owns it.
- **Handle the four delta operations distinctly.** `ADDED` produces new tests. `MODIFIED` produces **both**: new tests for the requirement's scenarios as revised, *and* an obsolete-tests list naming the tests bearing on the superseded behavior — a delta operation is not a reason to leave changed behavior uncovered, and a new test is additive so it does not reopen the path to editing an existing one. `REMOVED` produces an obsolete-tests list alone. Neither ever produces an edit.
- **Every obsolete-list entry carries its basis.** The list is the input to a human's *destructive* action, and the agent's additive-only guarantee stops at the report — so an entry made on grounds the reader cannot see relocates the loss rather than preventing it. The search is bounded to the dispatched test-path glob, each entry records the evidence it was matched on and is marked a candidate for confirmation rather than a conclusion, and finding nothing is stated explicitly, since an empty list reads as "none exists" while usually meaning "none was found". `RENAMED` is recorded as a rename. A change whose `.openspec.yaml` sets `skip_specs: true` has no scenarios to derive from: the agent reports that the existing suite must stay green through the change, and stops.
- **The agent only ever adds tests.** It never edits, deletes, or disables an existing test file. This is stated as a property a dispatcher can rely on without reading its reasoning, and is backed by a dispatch-declared test-path glob: a write outside that glob is a stop-and-report condition rather than a judgment call. The glob carries exactly one enumerated exception — the manifest at `<changeRoot>/test-manifest.md`, named in the spec rather than left to judgment — because a boundary with one named hole stays checkable while one admitting a judgment about legitimate locations reintroduces what the boundary removes.
- **Write `test-manifest.md` into the change root**, mapping each covered scenario to the tests that bear on it, with each assertion classified per `testing`'s specified/derived/deliberately-untested rule, plus the obsolete-tests list, any unresolved project questions with the assumptions taken, and the baseline in whichever form the testing floor permits. Every `#### Scenario:` in the delta specs is either covered or listed as uncovered with a reason — a countable completeness check rather than a judgment.
- **Add a `rules/` fragment** directing that the manifest be read before implementing a change. `openspec instructions apply` builds its `contextFiles` from the schema's artifacts, so a file that is not an artifact is not surfaced to whoever implements — the fragment is what closes that gap without touching OpenSpec-owned files.
- **Translate, rather than inherit, the floor obligations a subagent cannot discharge.** `skills/testing` directs that an unanswered project question be *asked*; a dispatched subagent has no channel to ask on. The agent is therefore supplied the project's convention-file paths, and records an unanswerable question in the manifest with the assumption it took and the tests depending on it. That is OpenSpec-specific adaptation of a floor rule, which the adapter design already licenses — not a second copy of the floor, and not a `SHALL` quietly skipped.
- **Carry the dispatch contract in the `description`.** The body loads only after the payload is fixed, so a contract stated only in the body is read by the agent and never by what feeds it. This follows `openspec-change-reviewer`'s precedent, which applies here with more force: two of the essential inputs cannot be derived from the change at all.
- Grant `Read, Grep, Glob, Write, Bash, Skill`, and state why each is needed. No new tag: `testing` and `openspec` are both already in the vocabulary.
- Cold-run the agent in an **isolated git worktree**, per `agent-authoring`'s requirement for a write-capable agent, with the drafted definition copied in and every writable payload path rewritten to the worktree root.

Deliberately **not** in this change: testing sections in `skills/python` and `skills/langgraph`; any mechanism gating task completion on tests passing; and any change to OpenSpec-owned files under `.claude/`, which are regenerated by `openspec update` and would lose an edit silently.

## Capabilities

### New Capabilities
- `change-test-authoring`: What a test-authoring pass over an OpenSpec change must do and where it stops — the dispatch contract that supplies the change rather than having it discovered, the scenario enumeration that makes coverage countable, the distinct handling of the four delta operations, the additive-only boundary and the path glob that backs it, deference to `skills/testing` for the testing standard rather than restating it, the manifest it produces and what that manifest must record, and the boundary that makes it a test author rather than an implementer.

### Modified Capabilities
(none)

`agent-authoring` governs *how* an agent is authored and places no constraint on subject matter. `change-review` governs the reviewer that runs before this agent and is untouched: this change adds no obligation to it and does not alter what it reviews. `testing-practice` is likewise untouched — this agent consumes that skill rather than changing it, and the capability records a dependency, not a modification. `toolkit-structure` already makes tags the only classification and requires only that existing vocabulary be checked before a tag is coined; no new tag is coined here.

## Impact

- **Affected**: new `agents/openspec-test-writer.md`, new `agents/openspec-test-writer.checks.yaml` for the recorded fixtures, and a new fragment under `rules/`. No existing asset changes except any recorded check fixture the invalidation sweep finds falsified.
- **Recorded checks elsewhere**: adding an asset invalidates the recorded checks of every asset it competes with. `openspec-change-reviewer` is the primary risk — both are dispatched against a named OpenSpec change, and a prompt like "get this change ready to implement" could plausibly reach either. `testing` is the second: it and this agent both answer to test-writing language, and the boundary is that the skill applies in the caller's context while the agent runs against a named change in its own. Both sets of fixtures are re-run as part of this change.
- **Isolation cost**: the cold-run check is materially more expensive than for a read-only agent — a worktree must be created, populated with the uncommitted definition, and every writable path in the payload rewritten. `agent-authoring` also requires stating that the worktree is not a sandbox: this agent holds `Bash`, which can address any path the process can reach, so the payload and the run's permission mode are reviewed before the run rather than treated as contained.
- **Dependency on a skill, not a copy**: the agent is thin only because `skills/testing` exists. If that skill's rules change, the agent inherits them with no edit — which is the point, and also means a change to `testing` should consider whether this agent's fixtures still hold.
- **No new dependencies, no tooling, no build step.** The agent runs whatever test command its dispatch names; it neither selects nor installs a runner.
