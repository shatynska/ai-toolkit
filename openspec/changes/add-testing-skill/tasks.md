## 3. Write the Skill

- [ ] 3.1 Create `skills/testing/SKILL.md` with the scope statement: language-agnostic, holds for any runner or project shape, and carries no version-dated claims — including a brief statement that this skill deliberately carries no "verified live against version X" line and why, per design.md Decision 6, so its absence is not read as an oversight. Keep this to the boundary itself; the supporting detail (that only `python-practice` and `langgraph-practice` mandate such a statement, so the divergence is from two of four precedents rather than a uniform one) belongs in the change record, not the body — see 2.4's exemption.
- [ ] 3.2 Write the **two entry situations** section, per design.md Decision 0: the target does not exist yet, or it already does; which rules bind in each; and that a test passing on first run is an alarm in the first and the expected result in the second. State explicitly that this is not an argument for writing tests first, so the section is not later read as contradicting the "not TDD advocacy" Non-Goal. Place it ahead of the four-states section (3.4), which depends on it.
- [ ] 3.3 Write the baseline section: run the existing suite and record what already failed before any new test is written, and state why a claim of failure is otherwise uninterpretable. Cover the case where **no baseline can be taken** — no suite, no runner, or a suite that cannot execute here — including the executable-but-impractical case (prohibitively slow, or needing credentials or services unavailable here). Present the **scoped** baseline — covering the tests bearing on the target, recorded with its scope — as a first-class permitted form rather than a fallback, since attributability is the requirement's purpose and a full run as default imposes a cost whose predictable adaptation is silent omission. Where not even a scoped baseline is possible, an explicit statement that none was taken and why is carried alongside any later failure claim. Neither silent satisfaction nor a reported-but-unrun baseline is permitted. State where a baseline is recorded.
- [ ] 3.4 Write the four-states section. Define each state by what it establishes — code ran and produced a wrong value; target absent so assertions are unverified; the test itself is broken so it establishes nothing; it passed on first run. **Name no state after a runner's phase, an error class, or an exit status**, per design.md Decision 1. State the enumeration for the absent-target situation and cross-reference 3.2 for how the second and fourth states read when the target already exists, rather than restating the list. State the third state as **situation-independent**: a defect in the test establishes nothing about the code either way, and repairing it moves the test to another state rather than producing evidence. Do not write that a repaired test yields a meaningless pass — that belongs to the fourth state. Write the **provenance rule** that separates the first state from the third, per design.md Decision 1: a specified assertion that mismatches means the code is wrong and the test is not a candidate for repair; only a derived assertion may be reconsidered, and then as a recorded change rather than a repair; a defect not in the expected value at all (wrong import, malformed setup) is the third state regardless. Without it the third state is a re-description available for any failure, and the never-weaken rule becomes satisfiable by relabelling. Route the remaining diagnostic question ("which state is this failure in?") to the language skills.
- [ ] 3.5 Write the target-absent prohibition: an absent target is an acceptable outcome, and creating the module, function, type, or empty stub to make tests execute is writing implementation. State that this is the most likely drift point, because it presents itself as repairing the tests. State both its scope and its lifting condition, per design.md Decision 8: it binds while the task's scope is writing tests, and where the same task also authorises implementation it lifts once the target-absent failure has been reported, after which the implementation is written as a distinct, announced step. What stays prohibited throughout is creating a target *in order to make tests execute*. An unbounded version would forbid ordinary red-green work and get overridden wholesale.
- [ ] 3.6 Write the level-selection rule: the level is the smallest unit that can observe the expected outcome, and a level above that minimum buys no additional evidence while costing speed and determinism.
- [ ] 3.7 Write the specified/derived/deliberately-untested section, including why an unlabelled derived assertion obliges an implementer to satisfy a constraint nobody agreed to, and why an uncovered case is recorded with its reason rather than omitted. State the recording surface — completion report, annotation alongside the tests, or either at the project's discretion — rather than requiring recording without saying where.
- [ ] 3.8 Write the never-weaken section: no editing an assertion to match observed output, no deleting or disabling a failing test to reach green, and a test superseded by a changed requirement is reported as superseded rather than quietly rewritten. State explicitly that describing such an edit as repairing a broken test does not exempt it, and cross-reference 3.4's provenance rule, which forecloses that route for a specified assertion.
- [ ] 3.9 Write the **bounded deference** section, per design.md Decision 8: a consuming project's `AGENTS.md`, `CLAUDE.md` and existing tests override this floor on level vocabulary, recording surface and stubbing approach; the never-weaken and target-absent prohibitions do not yield; a conflict is reported rather than silently resolved; and an absent convention produces a question rather than an invention. State which two rules are non-negotiable and why, so the boundary is reviewable rather than a matter of tone.
- [ ] 3.10 Write the pointer section naming every domain skill covering a stack with a testable artifact — `python`, `langgraph`, `bash`, **and `terraform`** — as where stack-specific testing material lives, directing that the matching skill be loaded **before** tests are written, and stating the reason (those skills carry the dated verification their claims require). Do not restate their content. Do not omit a skill for currently having thin testing content: that is a fact about its present state, not its scope, and omission would leave a request in that stack with no route onward. Note in the change record that these targets are currently thin — proposal.md scopes filling them as follow-on changes. Record a determination (do not assume, as task 6.2 requires for its own sweep) for every remaining library asset, naming why `n8n-workflow-review` and any other does or does not cover a stack with a testable artifact, so a later reader can tell the exclusion was reasoned rather than overlooked.
- [ ] 3.11 Write the **review and debug entry** section, per design.md Decision 2: the specified/derived classification is the review question, the four failure states are the debug vocabulary (a test passing when it should not is the fourth state), and rules that presuppose an authoring pass — baseline before writing, level for a test not yet written — are marked as such. Task 5.4 gates completion on the skill firing for these phrasings, so without this section it fires and supplies content for a task the user is not performing.
- [ ] 3.12 Review the whole body against the Non-Goals: no coverage policy, no framework API or fixture idiom, no test-suite architecture or CI shape, no advocacy for TDD as a methodology, no testing-genre catalogue. Remove anything a competent model already supplies unprompted so it does not displace the trap-focused content. Confirm specifically that 3.2's two-situations section reads as a statement of what each situation establishes, not as a recommendation to adopt one.
- [ ] 3.13 Check every example in the body: each must be marked illustrative rather than presented as verified behavior of a named tool, per the spec's *Guidance Is Language-Agnostic* requirement. Confirm separately that no **category** is language-shaped — the labelling rule does not substitute for design.md Decision 1's structural rule.

## 5. Trigger Check Under the Amended Standard

- [ ] 5.1 Build the fresh-context evaluator per `skill-authoring`: the candidate prompt plus the `name` and `description` of every asset in `skills/*/SKILL.md` and `agents/*.md`, **and** every skill and command committed under `.claude/` (`.claude/skills/*/SKILL.md`, `.claude/commands/**/*.md`). Derive both sets by glob, not from a fixed list. Nothing from the authoring conversation.
- [ ] 5.2 Record the amended pass standard before running, per design.md Decision 6: because overlap with the language skills is intended, a prompt routing to **both** `testing` and a language skill is a **pass**. Only displacement counts as a failure — `testing` routed to where a language skill should have been reached, or a language skill reached where `testing` should also have fired.
- [ ] 5.3 Run the first positive prompt: a stack-naming test-writing request ("write tests for this function" against a named language). `testing` must fire. A language skill firing alongside it is a pass, not a failure.
- [ ] 5.4 Run a second positive prompt on a **review or debug** phrasing ("review my tests for this module", "why does this test pass when it shouldn't"). The `testing-practice` spec's triggering requirement names writing, reviewing, and debugging, so a description could satisfy 5.3 while never firing on two of the three phrasings it mandates. `testing` must fire.
- [ ] 5.5 Run the negative prompt: an adjacent, plausibly-misfiring prompt outside scope — **splitting a slow suite across CI runners** (test-suite architecture and CI shape, both Non-Goals). `testing` must not fire. Do not use an unrelated prompt, which proves nothing. Do **not** use a coverage-target prompt here: choosing a coverage target is a testing question that a description written to counter under-triggering will plausibly reach, so failing on it would drive a narrowing loop against the breadth 5.3 and 5.4 require, with no tie-breaker. CI sharding is outside the subject entirely, which is what a negative prompt needs. Determine and record **which asset the evaluator holds should serve it** — or that none should, with the reasoning — per `skill-authoring`'s requirement that a negative fixture name the asset that should serve the prompt where one exists. A fixture asserting only "reaches nothing" is falsified silently by the next asset added.
- [ ] 5.6 Run a displacement probe in the reverse direction: a prompt that should reach a language skill on non-testing grounds ("review my Python script for bugs"). Confirm `testing` does **not** displace `python`. This is the risk design.md records as the intended-overlap failure mode and it is not covered by 5.3, 5.4 or 5.5.
- [ ] 5.7 Report all four outcomes. A positive-prompt failure (5.3 or 5.4) means the description is too narrow — widen and re-run. A negative or displacement failure (5.5 or 5.6) means it is too broad — narrow and re-run. The skill is not complete until all four hold. If widening and narrowing conflict across re-runs, stop and report rather than choosing between two artifacts' requirements unilaterally. Where a displacement traces to the **language skill's** description rather than to `testing`'s, also stop and report: editing another asset's description is outside this change's stated Impact, which admits no existing-asset edit beyond a falsified fixture, and needs a separate decision rather than a silent pass.
