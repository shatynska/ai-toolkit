## Context

The library ships seven skills (`bash`, `create-agent`, `create-skill`, `langgraph`, `n8n-workflow-review`, `python`, `terraform`) and one agent (`openspec-change-reviewer`). `bash`, `terraform`, `python`, and `langgraph` are the domain-asset precedents: general floors that state authoring discipline for a language or tool, deferring to a consuming project's own conventions on conflict. See proposal.md for the motivation and scope; this document covers how the skill is shaped.

Every one of those precedents is named for a **language or a tool**. This skill is named for a **practice**, and that difference drives most of what follows. A language skill inherits its boundary from its subject — `bash` stops where bash stops. A practice skill has no such edge: "testing" could mean anything from four failure modes to a book. The scope bar therefore has to be constructed in this change rather than inherited, which is the single most consequential thing this document decides.

A second difference follows from the first. This skill carries no dated verification statement, because it asserts nothing that could be verified that way. The precedent it diverges from is narrower than an earlier draft of this document claimed: checked against `specsRoot`, only `python-practice` and `langgraph-practice` *mandate* such a statement (`python`: "verified live against CPython 3.12.3, `ruff` 0.16.3, and `mypy` 2.3.0 on 2026-08-13"); `bash-practice` and `terraform-practice` require none, whatever their skill files may carry voluntarily. So this is a divergence from two of four precedents, not from a uniform one. It is still recorded, for the reason `add-bash-skill` and `add-python-skill` both gave — a later reader would otherwise read the absence as an oversight — but the rationale task 3.1 requires must state the two-of-four fact rather than the uniformity claim, which is false.

## Goals / Non-Goals

**Goals:**
- Ship testing guidance that changes agent behavior, concentrated on failure modes specific to tests being *authored by an agent* rather than by a person. Of the two named in proposal.md's Why, this floor squarely addresses one: an assertion edited to match observed output is carried by the never-weaken requirement. The **shared blind spot** between implementation and test is addressed only partially — the specified/derived/untested split forces assertions to trace to a stated requirement rather than to the code as written, which narrows it but does not close it. Closing it needs a test author that never sees the implementation, which is the deferred `openspec-test-writer`. Stated here so the goal matches what the floor delivers, and so Decision 5's scope bar is not read as having admitted more than it did.
- Make a claim about a test's failure interpretable: require a baseline, and distinguish what each failure state actually establishes.
- Keep the skill usable by hand, on any project, independently of the OpenSpec flow and independently of the agent proposed to follow it.
- Compose with the language skills rather than competing with them, matching how `python` and `langgraph` already relate.
- Set a defensible scope bar for a practice-shaped skill, since this is the first and every later one will cite it.

**Non-Goals:**
- Teaching testing to a human. A skill loads into an agent's context; it is not documentation the user reads. Same non-goal every existing domain skill carries.
- A coverage policy — target percentages, which modules must be tested, what ratio of unit to integration tests a project should hold. Those are project decisions and belong in a project's `AGENTS.md`.
- A test-framework tutorial or any framework's API. `pytest` fixtures, `bats`, `terraform test` — all stack-specific, all routed by pointer.
- Test-suite architecture at scale: directory layout, fixture-sharing strategy, parallelization, flake quarantine, CI shape. Out of the floor; a later change may add depth if use shows the need.
- Property-based, mutation, fuzz, contract, or performance testing as techniques. The floor covers what makes *any* test's evidence interpretable, not a catalogue of test genres.
- TDD as a methodology to advocate. The skill states what a test written before its implementation does and does not establish; it does not argue for a workflow.

## Decisions

**0. The skill states the two situations it can be entered in, because one of its central rules inverts between them.**
The floor was first drafted entirely for the case where tests are written before their target exists, and that was a mistake — Decision 2 argues the dominant trigger is "write tests for this function", which is usually a function that *already exists*. Two of the drafted requirements do not survive the move. The target-absent prohibition has no referent when the target is there. Worse, the fourth failure state inverts: a test that passes on first run is an **alarm** when no implementation exists (nothing could have satisfied it, so it asserts nothing), and the **expected result** when the code is already there (it establishes that the code currently behaves as asserted). A floor that states one reading and not the other would have an agent reporting correct characterization tests as defects on the most common prompt it receives. The remedy is to widen the content rather than narrow the trigger — narrowing was already considered and rejected under Decision 2, and that reasoning still holds. The skill therefore names both situations and marks which rules presuppose an absent target. This is deliberately *not* an argument for writing tests first: the Non-Goals exclude advocating TDD, and stating what each situation establishes is a different act from recommending one of them — the distinction is written into the requirement so a later reader does not resolve the apparent tension by deleting one side of it.

**1. Failure states are defined by what each establishes, never by the machinery that produced it.**
The four states were first drafted as "assertion failure / import-or-collection error / broken test / passes", and that draft was wrong. *Collection* is a `pytest` concept. A compiled language has no collection phase — an absent symbol is a build failure that takes the whole package down, and per-test granularity is simply unavailable; a shell script has no build step at all, and an absent function surfaces as a runtime failure inside a test that otherwise ran. Naming a state for one runner's phase would smuggle that runner's execution model into a skill claiming to hold across all of them. Defining each state by what it *establishes* — the code ran and discriminated; the target is absent and the assertions are therefore unverified; the test is broken and establishes nothing; it passed and is therefore an alarm — is language-neutral in a way the mechanism-named version is not. The diagnostic question ("which state is this failure in?") is genuinely language-specific and routes to the language skill under Decision 3. An alternative was considered and rejected: keeping mechanism names but marking the examples illustrative. That treats a labelling rule as a fix for a structural leak — the category would remain Python-shaped however its examples were labelled.

A second correction, and the more consequential one. Naming the third state at all creates a route around the never-weaken prohibition: an assertion edited to the observed value, then described as repairing a defective test, breaks no stated rule while doing precisely what the prohibition exists to stop — and that is the failure mode proposal.md's opening paragraph names as the reason for the whole change. Three fixes were considered. Routing the discrimination to the language skills under Decision 3 fails, because a mismatch between an expected literal and a produced value is not language-shaped, so the receiving skill would have no better basis than this one. Deleting the third state fails worse: a broken test is real and common, and removing the category pushes those failures into the first state, which the skill calls its strongest evidence. The fix adopted uses a classification the change already owns — assertion **provenance**, from the specified/derived requirement. A specified assertion that mismatches means the code is wrong, full stop; only a derived assertion may be reconsidered, and only as a recorded change to a derived assertion rather than as a repair; and a defect that is not in the expected value at all (wrong import, malformed setup) is the third state regardless. This passes Decision 5's filters — it changes what an agent does, and it is statable without naming a language.

One correction inside this decision, made after review. A draft glossed the third state as one that "turns into a meaningless pass once the defect in the test is repaired". That is wrong in both situations, not merely in one: where the target exists, repairing the test yields a genuine result; where it does not, repairing the test moves it to the second state rather than to any pass at all. The claim actually belongs to a test whose defect *is* that it asserts nothing, which is the fourth state. The third state is therefore stated as situation-independent — a defect in the test establishes nothing about the code either way — and this decision's risk entry about outcome-based definitions degrading correctly is about granularity, and never covered degradation across *situation*.

**2. The skill triggers on test-writing requests and accepts overlap with the language skills; it is not restricted to methodology questions.**
A review of an earlier draft recommended the opposite — scope `testing` to standards and methodology, and route requests to write test code to the language skill. That is recorded here as considered and declined, so it is not re-raised later as an oversight. Two reasons. First, it under-triggers on the dominant phrasing: users type "write tests for this function", not "help me with testing methodology", so a skill that disclaims the former goes dormant on the request that matters most — and countering under-triggering is exactly what `skill-authoring`'s description standard exists for. Second, it inverts the entry point the whole design rests on: `testing` is meant to be the reliable thing a test-writing task loads, whose pointer section then routes onward (Decision 3); a `testing` that does not trigger on test-writing leaves nothing reliable to enter through. Co-triggering is the intended outcome, not a collision — this skill supplies the standard, the language skill the idiom. `python` establishes the pattern: its description routes LangGraph specifics to `langgraph` while stating that its own traps still apply to LangGraph code. That precedent is **one-directional** — `langgraph`'s description names Python as a language but never names the `python` skill, and `langgraph-practice` carries no reciprocal cross-reference requirement the way `python-practice` does. It is cited here as the shape to copy, not as a mutual convention already in force; an earlier draft of this document described the two skills as "naming each other", which is not what the specs or the skill files say. The consequence for verification is recorded under Decision 6.

The trigger surface is **writing, reviewing, and debugging** tests, not writing alone. Reviewing and debugging are where this floor's rules are most directly applicable — "why does this test pass when it shouldn't" is state four, and "is this test any good" is the specified/derived distinction — so a description scoped to authoring would leave the skill dormant on the requests it answers best. This is recorded because an earlier draft argued only writing-versus-methodology, which would let a later reviser narrow the description to authoring and silently falsify both the spec requirement and the fixture that gates it.

Claiming that surface obliges the body to serve it. An earlier draft claimed write/review/debug in the description and in a gated fixture while every content requirement was framed for authoring — so the skill would reliably fire on "review my tests" and then supply instructions for a task the user was not performing. That is the under-delivery counterpart of under-triggering, and narrowing the surface is not the remedy: the mapping already exists here (the fourth failure state answers the debug phrasing, specified/derived answers the review phrasing), so the content simply had to be widened to state it. This is the same move Decision 0 made — a rule that behaves differently across entry conditions is fixed by widening the content, not by narrowing the trigger — and it is the second time that pattern has been the answer, which is worth noting for whoever extends this skill next.

**3. Language specifics are routed by a pointer to a sibling skill, not carried in this skill's `references/`.**
The alternative — `skills/testing/references/python.md`, `references/langgraph.md`, and so on — was seriously considered, on a real argument: a reference list inside a skill that has already loaded is visible in context, whereas a second, spontaneous decision to also load `python` is not guaranteed. It was rejected on three grounds. **Version-dating:** stubbing guidance for LangGraph placed under `testing/references/` would put claims dated against a specific `langgraph` version inside a skill that carries no dated verification statement and will not be re-verified when that library moves; re-verification follows the skill that owns the version claim, so the copy would rot silently. **Shape:** `testing/references/` would accumulate one file per language indefinitely, making every new language an edit to the testing skill and gradually making `testing` not about testing. **Reverse entry:** a request arising while editing a LangGraph file triggers `langgraph`, and material buried under `testing/references/` would be unreachable from the skill that actually fired. The reliability concern that motivated the alternative is answered by the mechanism rather than the location: *following a pointer that is already in context* is one step whether it resolves to a file read or to loading a named skill — what is unreliable is the unprompted decision to look, and a named pointer section removes that. If practice shows the hop being skipped, moving content into `references/` later is a file move, whereas silently drifted duplicate content is not detectable at all; the asymmetry favors this order.

**4. Flat `SKILL.md`, no `references/` split.**
`create-skill` defaults to a single flat file and splits only when the document stops being readable in one pass. `python` and `langgraph` pre-split because their trap surface was demonstrably wider than that budget at the outset. This skill's content is bounded by construction — the scope bar in Decision 5 admits a small number of requirements, and Decision 3 exports every language-specific expansion to a sibling skill, which is precisely the growth that would otherwise force a split. `bash` and `terraform` are the precedent being followed: flat, with `references/` left as an unused escape hatch. This is a projection, not a measurement, and is carried into tasks.md as a checkpoint to re-check against the actual draft rather than treated as settled here.

**5. The scope bar for this practice skill: a rule earns a place only if it changes what an agent does, and only if it holds without naming a language.**
Being the first practice-shaped skill, this needs stating rather than inheriting. Two filters, both necessary. The behavior filter is the same bar `bash` and `python` apply — general testing advice a competent model already supplies unprompted ("test edge cases", "keep tests independent") is excluded, and what survives is the material an agent gets wrong while appearing rigorous. The language filter is what keeps a practice skill from becoming a hub: a rule that cannot be stated without naming a runner belongs to that runner's skill. Applied to the material derived so far, the two filters admit the baseline requirement, the four states, the target-absent prohibition, the level rule, the specified/derived/untested split, and the never-weaken rule — and exclude coverage policy, framework idiom, and test-suite architecture, as recorded in Non-Goals.

**6. Verification is a trigger check under an amended pass standard; there is no live-verification step, and no dated statement.**
Every other domain skill in the library carries a dated verification line because each asserts version-dependent behavior. This one asserts none — that is a requirement in the spec, not an omission — so the live-verification discipline is satisfied vacuously and no dated statement is written. What replaces it is a sharpened trigger check. Because Decision 2 makes overlap intended, the ordinary pass standard ("the candidate prompt routes to this asset") would be wrong here: a prompt routing to both `testing` and `python` must count as a **pass**, and only *displacement* in either direction counts as a failure. The recorded fixtures for `python`, `langgraph`, and `bash` are re-run under that amended standard as part of this change, per proposal.md's Impact section.

**7. Name `testing`; one new tag, `testing`; no `allowed-tools`.**
The bare practice name matches the precedent of naming a skill after its subject rather than a paraphrase (`testing-practice`, `test-authoring`, `test-discipline` were considered and rejected on the grounds `bash`/`python`/`langgraph` already established — the capability is named `testing-practice`, the skill is not). No `allowed-tools`: this is open-ended guidance, not a wrapper around one external command, and it must not constrain the tools of whatever context loads it.

**8. Deference to consuming-project conventions is adopted, but bounded — and the boundary is stated rather than inferred.**
All four domain-skill precedents carry a *Consuming Project Conventions Take Precedence* requirement, and this document's Context places this skill in that archetype; an earlier draft asserted the archetype and then carried no such requirement, which left the skill presenting as the library's first floor that is also an authority. Blanket deference was considered and is wrong here for a reason the language skills do not face. `bash`'s preferences are preferences — a project that brackets differently is not defeating the skill. Two of this skill's rules are not like that: a project convention permitting an assertion to be edited to match observed output, or permitting the code under test to be created so tests can execute, does not adapt the practice to local circumstances, it deletes the thing the practice exists to prevent. A floor that defers on those two points asserts nothing at all. Blanket refusal was also rejected: level vocabulary, where a classification is recorded, and which stacks get stubbed are genuinely project decisions, and a skill that refused to yield on them would be wrong in the ordinary way the precedents guard against. The requirement therefore defers on everything except those two prohibitions and says which is which, so the boundary is reviewable rather than a matter of tone. The non-negotiable status inherits the target-absent rule's **scope bound**, and must not be read as widening it: what cannot be overridden by a project convention is creating a target *in order to make tests execute*, not implementing under a task that authorises implementation. Declaring an unbounded version non-negotiable would forbid ordinary red-green work, and a floor that forbids ordinary work gets overridden wholesale — carrying the never-weaken rule down with it, since both are declared non-negotiable together. The residual risk is that "non-negotiable" reads as this library overriding a consuming project; it is bounded to two rules, both stated with their reason, and the skill still requires the conflict to be **reported** rather than silently resolved — it does not authorise acting against a project convention unannounced.

## Risks / Trade-offs

- **The pointer section directs readers to skills that currently say nothing about testing.** `skills/python` has no testing content and `skills/langgraph` has one paragraph, so on day one the pointer is a promissory note and the skill's practical value rests on the floor alone. → *Mitigation*: accepted deliberately. The floor is independently useful, the pointer costs nothing while empty, and the two follow-on changes are already scoped in proposal.md. The alternative — deferring this skill until the language content exists — would delay the part that is useful now behind the part that is not.
- **Intended overlap (Decision 2) can decay into displacement.** A `testing` skill that fires on every stack-specific prompt could crowd out the language skill it is supposed to complement, producing tests that are methodologically sound and idiomatically wrong. → *Mitigation*: Decision 6's amended trigger-check standard tests for exactly this, in both directions, and the spec makes the co-trigger relationship an explicit description requirement rather than a hoped-for outcome.
- **The four states assume a granularity some languages cannot provide.** Where an absent target fails the whole build, individual tests have no state of their own, and the taxonomy applies to the run rather than per test. → *Mitigation*: Decision 1's outcome-based definitions degrade correctly — "the target does not exist yet, so the assertions are unverified" is true of a whole build exactly as it is of one test — and the diagnostic step that does need per-language detail is routed out under Decision 3.
- **The two non-negotiable rules (Decision 8) are a boundary this library has not drawn before.** Every other floor yields completely to a consuming project; this one does not, on two points. A project with a defensible reason to disable a test — a known-flaky integration test quarantined while its dependency is fixed — meets a rule stated as absolute. → *Mitigation*: the prohibition is on weakening or deleting a test **to reach green**, which is a statement about the motive and not about every deletion; and the requirement's reporting obligation means the conflict surfaces rather than being resolved in either direction silently. The residual risk is accepted and named rather than closed.
- **The scope bar (Decision 5) is a judgment first applied by its own author.** A later practice skill will cite it as precedent, so a bar set too loosely here propagates. → *Mitigation*: the bar is two explicit filters rather than a disposition, and the Non-Goals section names the specific expansions it excludes. An earlier draft also named `openspec-change-reviewer` as a mitigation here; that was circular — a risk whose mitigation is "a review will assess it" is unmitigated the moment a review passes — so the two filters and the Non-Goals list are the whole of it, and the residual risk is accepted rather than closed.
- **Flat structure (Decision 4) is projected, not measured.** → *Mitigation*: carried as a tasks.md checkpoint to re-check against the drafted body, with a split available if the projection proves wrong.

## Migration Plan

Not applicable. This change adds a new directory and modifies no existing asset, except for any recorded trigger-check fixture the invalidation sweep finds falsified. Nothing consumes `skills/testing/` at the time it lands, so there is no compatibility surface and no rollback beyond deleting the directory.
