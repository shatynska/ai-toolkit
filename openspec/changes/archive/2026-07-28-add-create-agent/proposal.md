## Why

`add-create-skill` listed "no authoring skills for agents or rules" as a non-goal, on the reasoning that agents are single files with small frontmatter and `plugin-dev` documents the format already. Checking that reasoning against the installed `plugin-dev` plugin and the 31 agent definitions shipped across the official marketplace shows it does not hold.

The documentation contradicts itself. `plugin-dev/skills/agent-development/scripts/validate-agent.sh` fails an agent that omits `model` or `color`, but 8 of 31 shipped agents omit `model` and 12 omit `color`, and all of them load. The same script warns when a `description` lacks `<example>` blocks, while `agent-development/SKILL.md` — in the same plugin — prescribes prose instead and relocates worked scenarios into the agent body; only 5 of 31 agents still use `<example>`. An `effort` field is used by 7 shipped agents and appears in neither document. Scoped tool grants are used by five agents — all in `claude-security`, carrying six grant expressions between them — and documented by neither. Following either source alone produces an agent that disagrees with practice.

The deeper gap is that an agent has a failure mode a skill does not. A skill's body is read by an agent that already holds the conversation. An agent's body *is* a system prompt executed in a fresh context, with no history, no shared working directory, and only the tools it was granted. `create-skill`'s apparatus tests one thing — does the description cause the asset to load. For an agent that is necessary and not sufficient: an agent can trigger perfectly and still fail because its body assumes context a dispatched subprocess never receives. Nothing in this repository or in `plugin-dev` tests that.

So the standard is a filter before it is a generator: its first obligation is to establish that an independent execution context is justified, and only then to author one. The cost that warrants the filter is not routing — a skill's description competes in the same dispatch decision an agent's does — but context. An agent's must be reconstructed by its dispatcher on the way in and collapses to a single report on the way out, and it has two surfaces to keep true rather than one, each carrying its own check.

That makes `create-agent` and `create-skill` a two-way router rather than two independent generators. `create-skill` already routes outward — "work that needs its own context or isolation → a subagent" — into a destination that does not yet exist. `create-agent` routes back, and closes the loop.

## What Changes

- Add `skills/create-agent/SKILL.md` — a skill, not an agent, parallel to `create-skill` and authored to `create-skill`'s standard. It covers:
  - **The routing gate, first** — before any authoring, establish that the work needs its own execution context. Work that belongs in the caller's context is a skill, a deterministic named sequence is a command, a standing instruction is a rule fragment. Recommending one of those and stopping is a complete outcome, and the gate names `create-skill` as the destination so the handoff is explicit rather than left to the user to rediscover.
  - **Frontmatter contract** — `name` and `description` required; `model`, `color`, `tools`, `effort`, and `metadata.tags` optional, recorded as a dated snapshot naming both sources it was read from and the corpus it was reconciled against, because the two shipped sources disagree with each other and with practice. The snapshot records the validator's constraints on the *values* as well as on which fields are present — the `name` pattern and length it errors on, the `color` set it warns outside of — so the standard's claim that a conforming agent produces exactly one warning ships with the conditions that make it true. `model` defaults to `inherit`, so declaring it for validator compatibility pins no model on a consuming project. `effort` is recorded with the values the corpus shows and an explicit statement that the accepted set is unverified — no published source mentions the field and the validator does not check it, so an enumeration would be invented rather than sourced, and the Shape checkpoint asks the author to confirm it. `metadata.tags` is what this repository's own conventions require of every asset and what neither shipped source mentions — no agent in the corpus declares `metadata` at all, so the loader's acceptance of it is established by observation before it is written into the standard.
  - **The `tools` field in full** — both syntaxes found in the wild (YAML array and bare comma list), least-privilege selection, and the scoped-grant form (`Agent(plugin:name)`, `Workflow(plugin:name)`) that lets an agent dispatch one specific subagent and which neither shipped source documents.
  - **The flat-file rule** — an agent lives at `agents/<agent-name>.md`; a subdirectory folds into the invocation name as `plugin:subdir:agent-name`, so a grouping decision becomes part of the name. The frontmatter `name` and the file name must agree, stated as a requirement of agreement rather than of precedence: the corpus contains no mismatch and the placeholder experiment only shows the file name used when no `name` is declared, so which wins is unobserved and rides along on a load this change already runs.
  - **Description standard** — inherited from `create-skill` (written against under-triggering, adjacent phrasings, library-wide disambiguation), using the prose trigger-summary form that `agent-development/SKILL.md` prescribes rather than the `<example>` blocks its own validator still asks for. The `Use this agent when [conditions]` opener is permitted: it addresses the dispatcher, not the user, and is what all three sources call for.
  - **System prompt standard** — second person, and the elements a fresh-context subprocess needs: a **dispatch contract** naming what the dispatcher must supply, absolute-path discipline, an untrusted-input stance toward everything the agent reads, a declared output format, and a stopping condition.
  - **HITL checkpoints** — Intent, Shape, and Draft, mirroring `create-skill`, with the routing gate evaluated at Intent.
  - **Post-write validation** — frontmatter parses, name matches the filename, the file sits directly in `agents/`, tags are well-formed, the `## When to invoke` section the description points at exists, and the body carries each required system-prompt element. It covers only what is knowable at write time; the fixtures file is a condition of reporting the agent complete, not a post-write check, since the checks that produce those fixtures have not run yet.
  - **Trigger check** — inherited from `create-skill`, run first because it is cheap and gates the expensive check. Its evaluator is scoped to this library and says so: widening it to whatever plugins happen to be installed would make the result depend on machine-local state, so the residual competition with published agent-authoring guidance is handled by disambiguation in the description and named as a residual risk rather than covered.
  - **Cold-run check** — new. A live half running the drafted agent in a context holding nothing from the authoring conversation, with one payload carrying only what its dispatch contract names, checked against declared output format, dispatch-contract completeness, termination, and lane adherence. A real dispatch is preferred because it enforces the tool grant; a simulation carrying the body verbatim is the fallback. Because every criterion but the tool grant is a judgment about what the agent returned, a dispatch form that surfaces only the dispatching session's summary counts as unavailable and falls back. The static half — reconciling the body's tool demands against the `tools` field — is mandatory in both forms: it is the fallback's only tool coverage, and beside a real dispatch it is a cheap redundancy that catches reaches the run never exercised. Its two behavioural criteria are stated as something a run can show: an incomplete dispatch contract is evidenced by the report resting on context the payload never supplied — asked for, blocked on, or silently assumed, the last being the form that actually occurs, since neither live form is interactive — and termination is judged by *why* the run ended, since an unbounded agent returns a truncated report rather than visibly running forever. Run in an isolated worktree when the agent holds write, edit, or shell tools, with the drafted definition **copied into the worktree** so the preferred form has an agent to dispatch at all — a worktree comes from a committed ref and the agent under authoring is untracked — with payload paths rewritten to it **and the run launched from it**, since a body using relative paths never touches the payload and would otherwise write into the authoring checkout, which is precisely the defect the check exists to catch. What the worktree contains is path-addressed writes; a shell grant reaches past it, and the standard says so rather than claiming total containment.
  - **Fixtures, not results** — the checks record their inputs (trigger prompts with expected routing, cold-run payload) in a companion `agents/<agent-name>.checks.yaml`, and record no outcome or run date. A body edit invalidates the cold-run check, so a stored pass is a claim about an agent that may no longer exist.
- Add the `AGENTS.md` pointer to `skills/create-agent/SKILL.md`, alongside the existing `create-skill` pointer. `create-skill`'s own description currently refers agent authoring to `AGENTS.md`, which carries no such standard; this closes that dangling reference.
- Make the routing explicit in both directions: `create-skill`'s existing outward route names `create-agent` as its destination, and `create-agent`'s gate names `create-skill` as its own.
- Widen `skill-authoring`'s trigger-check evaluator to span both skills and agents, since the harness selects across both in one decision, and state where the widening stops — this library, not other installed plugins. This is what tests that the two-way route is taken correctly rather than merely documented.
- Re-run and update `create-skill`'s recorded trigger check. Its recorded negative prompt — "write me a subagent that reviews my commit messages" — is correct only while no agent-authoring skill exists. This change invalidates it.

Non-goals for this change:

- **No agent is added to `agents/`.** This change adds the standard, not an asset written to it. `agents/` stays empty and keeps its placeholder.
- **No scripted validator.** `validate-agent.sh` exists and is referenced, not reproduced. Its overstated required-field checks are documented as such rather than corrected in a fork.
- **No `review-agent`** auditing agents already written.
- **No rule-authoring standard.** `rules/` remains uncovered, and the routing gate may point at it without a standard existing to receive the referral.
- **No new `toolkit-structure` constraint.** That capability places no restriction on non-`.md` files in `agents/`, so a companion file needs no exception from it and none is added. Its `SHALL` continues to bind placeholders only — the companion-file rule lives in `agent-authoring`, the capability that has one to govern. What the delta it does carry corrects is a factual error in its rationale, plus one scenario recording the `.md`-only behaviour as fact — see below.
- **No change to layout, tags, or plugin packaging.**

## Capabilities

### New Capabilities

- `agent-authoring`: The standard an agent definition in this repository must meet, and the workflow that produces one — the routing gate that must justify an independent execution context before authoring begins, the frontmatter contract reconciled across two disagreeing sources and the shipped corpus, the flat-file rule and its effect on invocation names, tool selection including scoped grants, the description standard for dispatch triggering, the system-prompt standard for a fresh-context subprocess including the dispatch contract, the human-in-the-loop checkpoints, post-write validation, and the two-stage verification of a trigger check followed by a cold-run check.

### Modified Capabilities

- `skill-authoring`: the trigger check's evaluator is widened from holding every skill's `name` and `description` to holding every skill *and agent* in the library, because the harness decides across both asset types in a single dispatch decision, with the boundary of that widening stated — the library, not other installed plugins, whose presence is machine-local and would make a check's result unreproducible; the same widening is applied to the two other requirements resting on the same premise, so a skill's description must disambiguate against every *asset* rather than every skill, and its tags must be drawn from the vocabulary across `skills/` and `agents/` rather than `skills/` alone; the existing "no skill is warranted" gate is made a named route to `create-agent` rather than an unaddressed referral; the standard gains the requirement that adding an asset invalidates the recorded checks of assets it competes with, which must then be re-run; and it gains the requirement that a trigger check records its fixtures and not its outcomes, without which the invalidation rule refers to recorded checks that nothing requires recording.

- `toolkit-structure`: one clause of the layout requirement's rationale is corrected. It currently reads *"Since every file directly inside `agents/` is read as an agent definition, a placeholder there SHALL take a form discovery ignores"* — but only `.md` files are read, which `agents/README.txt` records as an empirical finding and which is the reason a `.txt` placeholder satisfies that requirement at all. As written the sentence asserts that no ignorable form exists inside `agents/`, making its own requirement unsatisfiable, and it contradicts the fact `agent-authoring` depends on for the companion fixtures file. The corrected clause still binds placeholders and nothing else; a scenario is added recording that a non-`.md` file beside an agent is neither discovered nor a parse failure, which states a fact and imposes no obligation. No constraint is added or relaxed; a false statement of fact is corrected.

## Impact

- **New files**: `skills/create-agent/SKILL.md`, plus files under `skills/create-agent/references/` if the body outgrows one readable document — likely, given the frontmatter reconciliation table and the system-prompt standard.
- **Modified files**: `AGENTS.md` — one pointer line. `skills/create-skill/SKILL.md` — the outward route's named destination, the trigger-check evaluator wording and its stated scope boundary, the library-wide scope of description disambiguation and of the tag vocabulary, the fixtures rule and the report-versus-record distinction it needs, the rule that a fixture records the confirmed-correct routing rather than the observed one, the note that the third-person rule governs skills while agents may open `Use this agent when [conditions]`, the description-edit invalidation rule, its own recorded check reshaped to fixtures, and its **description**, which currently refers agent authoring to `AGENTS.md`. The description is where the dangling reference actually lives and is the field the re-run in this change evaluates, so it is edited before that re-run rather than left asserting a referral to a document that will defer to a skill it does not name.
- **Unchanged**: `agents/README.txt` stays; no agent is added, so the placeholder's stated lifetime has not ended.
- **Depends on** `add-create-skill` for the checkpoint sequence, the description standard, the isolated-evaluator trigger check, and the library-as-target rule, all of which this change inherits rather than restates where possible.
- **External sources are dated snapshots.** The frontmatter contract is reconciled from `plugin-dev/skills/agent-development/` and the marketplace agent corpus, both of which live outside this repository and drift. The standard records what was read and when, as `create-skill` does.
- **Ongoing effect**: authoring an agent by hand still works and is still discovered. What it lacks is evidence that the agent triggers and that its system prompt survives a cold dispatch. The routing gate also means a share of `create-agent` invocations should end with no agent written — that is the standard working, not failing.
- **No dependencies, no build step.** Markdown only.
