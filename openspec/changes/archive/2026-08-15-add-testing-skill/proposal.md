## Why

Tests written by an agent fail in ways tests written by a person mostly don't. When one agent writes both the implementation and its tests in a single reasoning trace, the two share blind spots — a case it didn't think of while coding is a case it won't think of while testing either. Sharper still is what happens under pressure to make a suite green: editing an assertion to match whatever the code actually produced is an available, cheap move for an agent, and it converts a test from a constraint on the code into a record of the code's current behavior. A test changed to fit the code it was written to constrain has stopped being a test, and nothing about the suite's output says so.

Around that sit failure modes that look like rigor and aren't: claiming a test is RED without knowing what was already failing before it was written; accepting a test that fails because of a typo in the test as evidence that the feature is missing; and never noticing a new test that *passes* before any implementation exists, which means it asserts nothing and will keep passing forever.

The library has nothing to say about any of this. `skills/python` carries no testing content at all; `skills/langgraph` carries a single paragraph on `.invoke()`/`.stream()` divergence. The gap is not Python-shaped — every item above holds identically in bash, Terraform, or TypeScript — so it belongs in a general asset rather than being split across the language skills, which is also what keeps it usable by hand on any project rather than only where a language skill happens to trigger.

## What Changes

- Add `skills/testing/` — a domain asset covering language-agnostic testing practice, held to `create-skill`'s standard, in the same archetype as `bash`, `terraform`, `python`, and `langgraph`: a floor of behaviors that read as rigorous but aren't, not a tutorial on how to write a test and not a coverage policy.
- Name the **two situations** a test-writing task arrives in — the target does not exist yet, or it already does — and state which rules bind in each. This is load-bearing rather than a caveat: a test passing on first run is an *alarm* where nothing could yet satisfy it and the *expected result* where the code is already there, so a floor stating only the first reading would have an agent reporting correct characterization tests as defects on the most common prompt it receives. It is not an argument for writing tests first; which situation a project works in is not this skill's concern.
- Adopt the archetype's **deference to consuming-project conventions, bounded by a stated floor**: level vocabulary, recording surface, and stubbing approach defer in the ordinary way, while two prohibitions do not — weakening, deleting, or disabling a test to reach green, and resolving an absent target by writing the code under test. A convention permitting either removes what the practice is for rather than adapting it, and a floor that defers there asserts nothing. The boundary is stated rather than left to tone, and a conflict is still reported rather than silently resolved.
- Scope the floor to what goes wrong when tests are authored by an agent: establishing a **baseline** (including what to do when no baseline can be taken at all) of what already failed before any claim about a new test's failure is made; the **four states a failing test can be in**, each defined by what it establishes rather than by the error that produced it (see below); the rule that a **target-absent failure is an acceptable outcome** and must not be resolved by creating the code under test, bounded by a stated lifting condition so it does not forbid ordinary work where the same task also authorises implementation; choosing a test's **level** by the smallest thing that can observe the expected outcome; separating assertions that trace to a stated requirement from those the author **derived**, and reporting a case deliberately left untested rather than omitting it; and never weakening or deleting an existing test to make a suite green.
- Define the four states **by what each establishes, never by the mechanism that produced it** — the code ran and produced a wrong value (strongest: the test executes *and* discriminates); the target does not exist yet (assertions never ran, so they are unverified); the test itself is broken (establishes nothing about the code in either situation, and is reachable only through a stated provenance rule — a **specified** assertion that mismatches means the code is wrong, not the test, so the state cannot be used to relabel an assertion edit as a repair); it passed before any implementation existed (an alarm, not a result). Naming a state after a language's machinery — pytest's *collection* phase, a compiler error, a shell's "command not found" — would smuggle one execution model into a skill claiming to hold across all of them, since a language with no collection phase cannot produce per-test granularity at all. **How to tell which state a given failure is in** is language-specific and belongs in the language skill, not here.
- Carry a **pointer section**, not language content: a named list directing the reader to load the matching domain skill before writing tests in that stack. The list names **every domain skill covering a stack with a testable artifact** — at least `python`, `langgraph`, `bash` and `terraform`, with `n8n-workflow-review` determined during tasks rather than settled here — not only those whose testing content is already written; omitting one for currently being thin would leave a request in that stack reaching this floor with no route onward. Language- and tool-specific testing material stays in those skills, which own the version-dated verification the claims need — this skill asserts nothing version-dependent and states that as its boundary.
- Trigger on requests to **write, review, or debug** tests, **not** on testing-methodology questions alone. Reviewing and debugging are where the floor's rules apply most directly — "why does this test pass when it shouldn't" is the fourth failure state, "is this test any good" is the specified/derived distinction — so a description scoped to authoring would leave the skill dormant on the requests it answers best. The description must fire on the dominant phrasing ("write tests for this function"), because a skill that disclaims it goes dormant on the one prompt that matters most, and under-triggering is the failure `skill-authoring`'s description standard exists to counter. Overlap with `python`, `langgraph`, and `bash` on such a prompt is the intended outcome rather than a collision — this skill supplies the standard, the language skill supplies the idiom — following the co-triggering shape `python` already sets, whose description routes LangGraph specifics onward while stating that its own traps still apply to LangGraph code. That precedent is one-directional — `langgraph` does not name `python` in return — so it is copied as a shape rather than cited as a mutual convention already in force.
- Introduce one new tag, `testing`.
- Re-run the recorded trigger-check fixtures of every existing asset this skill competes with, per the invalidation requirement in `skill-authoring`. `python`, `langgraph`, and `bash` are the primary risk.

Deliberately **not** in this change, and each independently proposable afterward: the `openspec-test-writer` agent that would apply this standard inside the OpenSpec flow, testing sections in `skills/python` and `skills/langgraph`, and any mechanism that gates task completion on tests passing.

## Capabilities

### New Capabilities
- `testing-practice`: What the library's testing guidance asserts and where it stops — language-agnostic scope and the no-version-dated-claims boundary that sustains it, the two situations a test-writing task arrives in and which rules bind in each, the baseline requirement that makes a failure claim interpretable together with the unobtainable-baseline case, the four-state taxonomy defined by what each state establishes rather than by the machinery that produced it, which states are acceptable evidence, the prohibition on resolving a target-absent failure by writing the code under test, the level-selection rule, the specified/derived/untested distinction that keeps a test author from silently designing behavior and the surface those classifications are recorded on, the prohibition on weakening an existing test, the pointer discipline that routes language specifics to the skill that verifies them, the triggering stance that accepts overlap with the language skills rather than partitioning by subject, and deference to consuming-project conventions bounded by two prohibitions stated as non-negotiable.

### Modified Capabilities
(none)

`skill-authoring` governs *how* a skill is authored and places no constraint on subject matter. `toolkit-structure` already makes tags the only classification and requires only that existing vocabulary be checked before a tag is coined — which this change does rather than changes, and its "adding an asset requires no catalogue update" requirement means no README or index edit is owed. `python-practice` and `langgraph-practice` are untouched here: this change adds no testing content to those skills and only names them as pointer targets, so their requirements do not change.

## Impact

- **Affected**: new directory `skills/testing/`. No existing asset changes except any recorded trigger-check fixture the invalidation sweep finds falsified, which is then updated in this change rather than a later one.
- **Recorded checks elsewhere**: adding an asset invalidates the recorded trigger checks of every asset it competes with. `python`, `langgraph`, and `bash` are the primary risk, since a testing request arising during work in any of those stacks reaches both them and this skill. Because overlap is intended here rather than avoided, the fixtures must be re-run against a standard that treats co-triggering as a pass and only a *displaced* language skill as a failure. `terraform`, `n8n-workflow-review`, `create-skill`, `create-agent`, and `openspec-change-reviewer` are lower risk, but the sweep is a determination to be run during tasks, not assumed here.
- **Library positioning**: this is the library's first **practice-shaped** skill — every existing skill is named for a language or tool (`bash`, `terraform`, `python`, `langgraph`, `n8n-workflow-review`), so there is no precedent for how broad a practice skill should be, and the scope bar has to be set in this change rather than inherited.
- **Verification discipline**: the library's live-verification requirement for version-dependent claims is satisfied here by the skill making none. Any failure output shown as an example is a language-flavored illustration of a language-agnostic distinction and must be marked as illustrative rather than presented as verified behavior of a named tool version. This is a labelling rule and does not substitute for the structural one above — a state defined by a language's machinery stays a scope leak however its examples are labelled.
- **No new dependencies, no tooling, no build step.**
