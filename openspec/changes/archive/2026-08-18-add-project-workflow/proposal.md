## Why

The library has assets for working *inside* a project that already has a process — `create-skill`, `create-agent`, `testing`, `openspec-test-writer`, `openspec-change-reviewer` — and nothing for establishing that process in the first place. A new project starts as an empty directory, and everything that makes the rest of the library usable (Git, OpenSpec, a conventions file naming the workflow) has to be remembered and reassembled by hand each time.

The obvious framing is that this is a setup problem, and the obvious fix is a script that runs `git init` and `openspec init`. That framing is wrong about where the inconsistency actually lives. Nobody starts a project and forgets `git init`; the step is mechanical, immediate, and its absence is loud. What is genuinely forgotten is the set of decisions that have no natural moment and no artifact demanding them — what the testing strategy is, what the architecture is, and above all what is deliberately *out* of scope. Those get settled implicitly by the first few commits and are never written down, which is precisely the state the rest of the library assumes has already been avoided.

The evidence for that claim is in this change's own history. The exploration that produced it listed eleven foundation questions in a considered design document, and that list still filed three deliverables (README contents, `.gitignore` sufficiency, project-specific conventions) as though they were open questions, while omitting non-goals entirely — the single question whose absence does the most damage six weeks in. A carefully written list drifted. An unstructured conversation starting cold each time will not do better, and `/opsx:explore` is explicitly unstructured by design: "no fixed steps, no required sequence, no mandatory outputs."

So this change ships two halves. The deterministic half is cheap and worth automating because it is cheap. The judgment half is where the value is, and it needs a coverage gate — something that guarantees no decision is silently skipped — without becoming an interrogation, which would make the discovery conversation worse rather than better.

The two halves also differ in how far they can travel. Deterministic setup is a shell script and needs no agent at all; foundation discovery is a conversation and has no non-agent equivalent. This change takes that split seriously rather than packaging both as Claude Code assets: the methodology is a script plus markdown, and Claude Code is a wrapper over it.

## What Changes

### The deterministic half is a standalone tool, not a skill's implementation detail

- **Add `scripts/project-init`**, a shell script runnable by a human, a shell, a CI job, or any agent in any harness. A script buried at `skills/project-init/scripts/` is reachable only by a harness that implements skills and loads the `SKILL.md` naming it — Codex and Antigravity have no skills primitive, would never load it, and would reasonably read a `skills/` path as "not mine." Placing the entry point at `scripts/` is what makes the stated goal of a model-independent workflow true rather than aspirational.

- **`--help` is the tool's interface, and it is the portable equivalent of `SKILL.md`.** A skill file is readable only by harnesses that implement skills; `--help` output is readable by anything that can run a shell. The script SHALL document its modes, flags, and exit codes there, so no privileged reader is required to learn what it does.

- **The caller resolves the toolkit root by an ordered chain, with Claude Code as one option rather than a requirement**: `$AI_TOOLKIT_ROOT` first (explicit, portable, any harness), `$CLAUDE_PLUGIN_ROOT` second (zero setup when running as an installed plugin), then the machine-local `~/projects/ai-toolkit` — a convention this repository already documents for `@` importing rule fragments. If none resolves, the caller reports itself blocked and invokes nothing. A person who types the path has already resolved it and is subject to none of this.

- **Once running, the script locates its own resources and consults no environment variable.** It derives its directory from its invocation path. Resolution therefore happens exactly once, in the caller — a script that re-resolved could inline text from one copy while stamping the version of another, which is the one thing the marker exists to make reliable.

- **Neither the caller nor the script falls back to improvising.** A caller that cannot find the script reports blocked; a script that cannot find its fragment reports `BLOCKED` and its caller relays that rather than reinterpreting it. An inline fallback — having a model run the underlying commands directly — would produce a differently initialized project (no managed block, no marker, no version stamp) while reporting success, which is precisely the silent divergence this change exists to prevent.

- **`--tools` is a passthrough flag, not a hardcoded `claude`.** `openspec init` accepts around thirty tool targets including `codex`, `antigravity`, `cursor`, `gemini`, and `agents`. Hardcoding `claude` would make every bootstrapped project Claude-shaped at the OpenSpec layer regardless of what its developer actually uses, undoing the portability established everywhere else.

### Failure semantics are part of the contract, not a formatting concern

- **Every run terminates in exactly one of three outcomes — `SUCCESS`, `BLOCKED`, or `ERROR` — and the exit code agrees with it.** `SUCCESS` exits 0. `BLOCKED` means a precondition was unmet and nothing was attempted (no fragment, missing `git` or `openspec`) and exits non-zero — which requires every precondition to be checked *before* any concern is attempted, since a fragment read only at the point of use would report `BLOCKED` after the repository had already been initialized. `ERROR` means a step was attempted and failed, and exits non-zero with a code distinct from `BLOCKED`. A tool that prints `BLOCKED: toolkit root not found` and exits 0 is worse than one that crashes, because CI and shell callers believe it. This becomes load-bearing precisely because `scripts/project-init` is now a standalone executable rather than something only a model reads.

- **A partial run reports exactly what it completed before failing, and re-running is the recovery path.** Bootstrap does not roll back — a `git init` that succeeded before `openspec init` failed stays. This is safe only because per-concern idempotency already guarantees a second run skips what exists and completes what does not, which turns "what state am I in after a failure?" from a question into a re-run. Idempotency was adopted for adoption support; failure recovery is the second thing it buys.

### What bootstrap does and refuses to do

- **Two modes, behaviorally distinct, split on one observable.** The split is whether the repository has at least one commit: no commit is *new project* mode, which ends by naming foundation as the next step; at least one is *adoption*, which ends at the managed workflow block. A single observable is necessary because a directory where `git init` ran but nothing was committed is neither "no repository" nor "a repository with existing code", and would sit unclassified under the intuitive phrasing. Each concern is checked independently — Git initialized? OpenSpec present? conventions file exists? marker absent? — so both modes share one code path, and neither refuses to run because some steps are already satisfied. The alternative ("stop if the directory already looks initialized") is more fragile for no benefit: it makes reruns unsafe and makes adoption a future rewrite instead of a behavior that already falls out.

- **Adoption does not create a `project-foundation` change**, and this is a decision rather than an omission. An existing repository's architecture, stack, and testing approach are already embodied in its code; asking it to re-derive them would invent a discovery phase for decisions that are no longer open. Recording them retroactively is legitimate and often valuable — it is a normal change the user proposes when they want it, and the adoption report names foundation as available for exactly that purpose rather than leaving the option undiscoverable.

- **Bootstrap never overwrites a file the project already has — bounded to its own writes.** A missing `.gitignore` is created; an existing one is left exactly as found and reported, never merged or extended. A missing `AGENTS.md` is created; an existing one receives the managed block and nothing else is touched. A script that edits files it did not write cannot distinguish a deliberate project decision from an oversight. The bound is explicit because bootstrap delegates specification-tooling initialization to an external command whose writes it does not control: those are reported and attributed, not prevented, and an unbounded claim would be false on the adoption path.

- **"Minimal" `.gitignore` is enumerated, not adjectival.** Three categories — environment files, OS artifacts, editor directories — written out verbatim in the specification itself, not in a design document that is archived with the change while the requirement outlives it. The requirement carries the entries and no count: a number restated elsewhere is one more thing that drifts, which is the failure the enumeration exists to prevent. Bootstrap cannot know the stack, and a generic template is actively misleading: `node_modules/` in a Python project asserts something false about it. Naming the exact contents is what stops "minimal" from growing into twenty patterns while still being called minimal. Stack-specific exclusions become a foundation task, which also removes "is the generated `.gitignore` sufficient?" from the question list by making it a deliverable.

- **Completion is an enumerated observable outcome.** The report lists each concern and what happened to it (created, skipped-because-present, failed), plus the workflow version inlined, plus the next step. "Successful initialization" is a checklist a reader can verify rather than a claim they must accept.

### The workflow rules travel as markdown, not as a copy

- **Add `rules/development-workflow.md`** carrying the generic rules: spec-driven development, test design before implementation, independent review after it, verification before any completion claim, small focused commits suggested and never made automatically, scope control, and the repository rather than conversation history as the source of truth.

- **Bootstrap inlines that fragment into a versioned managed block** in the project's `AGENTS.md`, delimited by `<!-- ai-toolkit:development-workflow vN -->` markers and carrying a do-not-edit notice inside the opening marker. A plain copy would freeze a snapshot into every project and leave workflow improvements undetectable and unpropagatable. A marked block keeps the copy honest: it records which version was inlined, it is greppable, and it gives a later sync a boundary it can refresh without touching what the project wrote below it. Content between the markers is defined as generated and replaceable; everything outside belongs to the project. No update command ships here — the marker is shaped so one is possible without re-parsing hand-written text.

- **`AGENTS.md` is the portability win, for the harness it was empirically confirmed on.** Codex and Antigravity are documented to read `AGENTS.md` as their native conventions file, with no import indirection — unlike Claude Code, which this change confirmed (task 1.6) does *not* load `AGENTS.md` unless `CLAUDE.md` imports it. The Codex/Antigravity claim is asserted rather than observed in this session (task 1.7, no way to invoke either non-interactively here); if it does not hold, the claim narrows rather than the design changing, since the report-the-import-line fallback this change added for Claude Code would cover any harness with the same indirection.

- **The marker replaces the state file the exploration originally proposed.** A `project-state.json` holding `phase`, `status`, and `current_change` was designed and then dropped: nothing read its contents (only its existence, and only to answer "is this initialized?"), nothing would ever have updated it, and every field it held is derivable from the sources this workflow names as authoritative — `openspec list` for the current change, the archive for whether foundation is done, `git status` for uncommitted work. It would have been wrong on day two with nothing to detect it. The marker answers the two questions that are *not* derivable: is this workflow adopted here, and at which version.

- **Bootstrap reports the workflow version it inlined.** Plugin installation is version-pinned, so a project can be bootstrapped from an older cached toolkit than the repository holds with nothing in the resulting files saying so. Stating the version in the report, and stamping it into the marker, makes that visible when it happens. Setting `$AI_TOOLKIT_ROOT` to a working tree bypasses the pin entirely, which is what a toolkit developer wants.

- **Rules name a role, then bind it to a tool.** The text states the obligation ("have an independent author derive tests from the delta specs before implementing") and names `ai-toolkit:openspec-test-writer` beneath it as the Claude Code binding. Naming the agent bare would put a dangling reference into every project without the plugin, making Claude Code a hard dependency of the methodology rather than its first adapter.

### The judgment half

- **Add `rules/project-foundation.md`** carrying the decision checklist: what the project is, what problem it solves, its scope, **its non-goals**, its audience, its language and framework, its architecture, its testing strategy, and its development tooling. Non-goals is added as a first-class question rather than inherited from the exploration's list, which omitted it. Putting the checklist in a fragment rather than inside `SKILL.md` is what lets a non-Claude tool follow the same procedure — and it is far cheaper now than retrofitting once a skill owns the text. Unlike `development-workflow.md`, this fragment is **not** inlined into `AGENTS.md`: it is a one-time procedure, not a standing rule, and inlining it would leave permanent clutter in every project. (The checklist itself, not the decisions it settles — those do reach `AGENTS.md`, in a separate section; see *Foundation surfaces beyond the change itself*, below.)

- **Add `skills/project-foundation/`** as the conversational wrapper over that checklist. The fragment carries the decisions and the exemption; the skill carries the gate and the conversation quality. It does not fire the questions in sequence — identity and scope must come from the user, while technical decisions may be proposed with reasoning and confirmed, which is faster than being asked. The skill's contribution is coverage, classification, and a stop condition.

- **Coverage is checkable in the artifact, not only in the conversation.** The foundation change's `design.md` carries a fixed set of named sections, one per decision, so "was everything covered?" is answered by reading a file rather than by trusting a conversation went well. A gate that exists only inside an LLM exchange is not a gate.

- **The skill writes as it goes and hands off to change authoring.** It creates the change early and lands each decision as it settles, rather than accumulating answers until a final write — a foundation conversation plausibly spans sessions, and the workflow rule this same change ships forbids relying on conversation context for what an artifact could hold. Change authoring is not reimplemented: `openspec-propose` already turns a description into proposal, design, and tasks.

- **State the foundation change's test exemption explicitly.** The workflow requires dispatching `openspec-test-writer` before implementing a change, but that agent's dispatch contract requires the test command and test-path glob — outputs of the foundation change, not inputs to it. Foundation is the one change in a project's life for which test authoring is structurally impossible. Unstated, an agent reaching this point either stalls or invents a placeholder suite.

- **Foundation is complete when its sections are filled and the change is archived**, and it stays complete afterwards. It is a historical change, not an invariant: a later architectural shift is a new change, not a foundation violation.

- **Foundation surfaces beyond the change itself.** `design.md` is the canonical, checkable record, but it is archived with the change and not what a human or a fresh agent session reads by default. As identity, problem, audience, scope, non-goals, technology, and architecture settle, they are also written into the project's `README.md`; as testing strategy and development tooling settle, they are also written into a new, project-specific section of `AGENTS.md`, separate from the existing managed workflow block. The split follows an auto-load test, not an audience guess: `AGENTS.md` is what this change already confirmed (task 1.6) Claude Code loads into every session via the `CLAUDE.md` import, `README.md` is not — so only the two decisions a later change's test-authoring step actually depends on (the test command, the test-path glob) go where they reach an agent without being told to look.

### Claude Code is the wrapper, added last

- **Add `skills/project-init/SKILL.md`** as a thin adapter that resolves the toolkit root, invokes `scripts/project-init` through its interpreter (`bash "<root>/scripts/project-init"`, sidestepping any dependence on the executable bit surviving plugin extraction), relays the report, offers an initial commit and waits for confirmation, then names the next step. It never takes that next step: continuing automatically into a discovery conversation would decide that this is the right moment to spend an hour on foundation, which belongs to the user.

- **Both skill descriptions must draw a legible boundary** — deterministic environment setup versus foundation decisions — since "set up a new project" could plausibly reach either, or reach `create-skill`. `skill-authoring` requires that boundary be *observed* in a trigger check, not judged from a well-written draft.

Deliberately **not** in this change: the `SessionStart` hook that detects an uninitialized directory; any lifecycle validation, enforcement, or state machine; a `/project-update` that refreshes an outdated managed block; machine-readable report output (`--json`); a `README.md` written by *bootstrap* specifically (`scripts/project-init` never writes one — foundation does, once decisions settle; see *Foundation surfaces beyond the change itself*, above); any attempt to check whether a project still *matches* its foundation; and any change to OpenSpec-owned files under `.claude/`, which `openspec update` regenerates and would silently discard an edit to.

The hook is deferred rather than dropped. It is the highest-risk and lowest-value piece of the original design: "is this a project directory?" has no reliable answer, a `SessionStart` hook fires every session so a false positive becomes permanent noise in every scratch directory where the plugin is installed, and it addresses "I forgot this command exists" — a one-time learning problem rather than a recurring one. It should be added once the workflow has proven worth being reminded about.

## Capabilities

### New Capabilities

- `project-bootstrap`: What initializing a project into this workflow must do and where it stops — the standalone tool at `scripts/` with `--help` as its portable interface, the ordered toolkit-root resolution that treats Claude Code as one option, self-location once running, the refusal to improvise when unresolvable, `--tools` as passthrough, the three terminal outcomes and the exit codes that must agree with them, partial-run reporting with re-run as the recovery path, the two modes and what behaviorally separates them, per-concern idempotent checking serving both from one path, the create-what-is-absent-report-what-is-present rule, the enumerated minimal `.gitignore` and what is deliberately left uncreated, the managed block carrying rules and version into a project's conventions file, the marker as adoption signal, version reporting against a version-pinned install, and the enumerated completion report that names the next step without taking it.

- `project-foundation`: What establishing a project's foundation must cover and how — the decisions that must be settled including non-goals, the checklist living in a portable fragment with the skill as conversational wrapper, the split between decisions that must be supplied and those that may be proposed and confirmed, coverage as a completion gate expressed in named artifact sections rather than conversation order, incremental persistence so a multi-session conversation survives its sessions, the handoff to change authoring rather than a second implementation of it, the test-authoring exemption applying to this change alone, archival as the completion signal, and surfacing settled decisions into the project's `README.md` and `AGENTS.md` — split by an auto-load criterion rather than by audience — so the record outlives the archived change.

### Modified Capabilities

- `toolkit-structure`: Four widenings. First, *Rules are consumable by import path* records the `@` import as how a `rules/` fragment reaches a project; this change adds a second path — a fragment read from the toolkit root by a shipped script — available because plugin installation copies the entire repository tree rather than only the directories backing a Claude Code primitive (verified against the local plugin cache, which contains `rules/`, `openspec/`, and root documentation alongside `skills/` and `agents/`). "Rules are not carried by the plugin" is true of the *primitive* and false of the *files*, and the specification records only the first reading. Second, `scripts/` introduces a third top-level category — shipped executable tooling, distinct from the library assets in `skills/`, `agents/`, and `rules/` and from the repository-only tooling in `.claude/` — and the requirement separating those two currently admits no third. Third, `rules/` must be stated to hold both standing constraints intended for a project's conventions file and one-time procedural checklists that are not, since `project-foundation.md` is the first of the latter and nothing currently distinguishes them. Fourth, *Repository is browsable without an index* forbids repository-level scripts and dependencies and admits executable code only inside an individual skill; it is widened to admit shipped tooling at `scripts/` and a dependency-free harness at `tests/`, while keeping the no-build-step, no-dependency-manifest and no-catalogue constraints intact. Without this widening the change would archive a specification the repository visibly violates.

`skill-authoring` governs how a skill is authored and places no constraint on subject matter; both new skills are held to it without it changing. `change-review`, `change-test-authoring`, and `testing-practice` are untouched — this change consumes those agents and that standard by reference from the workflow rules, which records a dependency rather than a modification.

## Impact

- **Affected**: a new `scripts/project-init`; two new rule fragments (`rules/development-workflow.md`, `rules/project-foundation.md`); two new skill directories (`skills/project-init/`, `skills/project-foundation/`), both holding only a `SKILL.md`; four widened `toolkit-structure` requirements; and the repository's first test harness. This repository's own `AGENTS.md` and `README.md` are updated where they describe the repository's categories and how rules reach a project. Separately, `rules/project-foundation.md` and `skills/project-foundation/SKILL.md` gain the README.md/AGENTS.md surfacing behavior (task section 10), which changes what a *consuming* project's own `README.md` and `AGENTS.md` receive once its foundation settles — distinct from this repository's own documentation update above.

- **This change introduces testing to a repository that has none.** There is no `tests/` directory, no bats, no runner, and no test configuration anywhere in the repository — every asset shipped so far has been markdown, verified by review and trigger checks rather than by execution. `scripts/project-init` is the first executable, and the scenarios it needs covered are concrete: empty directory; existing Git repo; existing OpenSpec; existing `.gitignore`; existing `AGENTS.md`; existing managed block; unresolvable toolkit root; missing fragment; repeated execution producing no destructive change; and adopting `ai-toolkit` itself. Those become scenarios in the delta specs. This first suite is written directly rather than dispatched to `openspec-test-writer`, whose contract requires a test command and test-path glob that do not exist until the harness creates them — the same structural bootstrap the foundation exemption records, and it is recorded as an exemption rather than left implicit. The *runner* is a genuine new decision, and choosing between bats (idiomatic, an added dependency) and a plain shell harness (zero dependency, consistent with a repository that has no build step) is the largest piece of previously unnamed scope here.

- **The script inherits an existing completion standard rather than inventing one.** `skills/bash` requires a clean ShellCheck run as necessary-but-not-sufficient for completion, together with an explicit statement of the obligations ShellCheck does not check. `scripts/project-init` is held to that, so shell quality needs no new rule.

- **Portability is a stated constraint, not an aspiration.** `#!/usr/bin/env bash`, and no feature newer than bash 3.2 — the version macOS still ships — so the script behaves identically on macOS, Linux, and Git Bash on Windows. "POSIX-compatible" would be the wrong constraint to state, since the shebang selects bash; the precise one is bash without 4.x-only constructs such as associative arrays or `${var,,}`.

- **The skills stay thin, which is the point.** Moving the script to `scripts/` means neither skill ships a supporting file. Note that `toolkit-structure` already permits a skill to bundle code under its own `scripts/` directory, so this is a choice between two allowed placements rather than a question the change leaves open — and the reason for choosing the root is reachability by harnesses that never load a `SKILL.md`.

- **The placement overrides an existing constraint, which is why a fourth widening is needed.** *Repository is browsable without an index* forbids "no script that operates on the repository" and carves out only a skill's own `scripts/`, on the reasoning that such code ships to a consumer. Shipped tooling at the root meets that same test, but the text does not admit it — and it forbids `tests/` outright. Both are widened explicitly rather than broken silently, keeping the constraints that still hold: no build step, no dependency manifest, no catalogue, no machinery this repository runs on itself.

- **Three unverified assumptions about harness behaviour, all tasked before implementation.** Invoking through `bash` removes any dependence on the executable bit, but three claims remain. Whether Claude Code loads a project's `AGENTS.md` when no `CLAUDE.md` imports it (task 1.6) — the one that decides whether the workflow rules land in force or inert on the harness this library primarily serves. Whether Codex and Antigravity read `AGENTS.md` natively, asserted above as the portability win and not yet observed (task 1.7); if it does not hold, that claim narrows rather than the design changing. And whether `$CLAUDE_PLUGIN_ROOT` resolves at skill runtime — the mildest of the three, since it sits second in a chain and failure degrades to the machine-local path rather than breaking the tool.

- **Version skew is visible but not prevented.** Bootstrap reads the fragment from wherever the resolution chain lands, so an installed plugin yields its pinned version. The report surfaces this; nothing here reconciles an outdated install. That is what a future update command is for.

- **A one-time procedure now lives in `rules/`.** `project-foundation.md` is a checklist, not a standing constraint, and it is the first fragment not intended for `AGENTS.md`. The `toolkit-structure` widening above is what keeps that from becoming silent precedent.

- **Recorded checks elsewhere**: adding skills invalidates the recorded triggering checks of every skill they compete with. `create-skill` and `create-agent` are the primary risk, since a prompt about "setting up a new project" could plausibly reach an authoring skill; the two new skills also compete with each other.

- **This repository is the first adoption test case.** `ai-toolkit` has Git, OpenSpec, and an `AGENTS.md` with no managed block. Running the tool here should take the adoption path: skip Git and OpenSpec, leave `.gitignore` and `AGENTS.md` content untouched, add the managed block, and stop without proposing a foundation change — exercising the mode split and the never-overwrite rule against a real repository rather than an empty directory.

- **No new runtime dependencies.** The script requires `git`, `bash`, and the `openspec` CLI, all already prerequisites for working in this repository. A test runner may add a development dependency, which is the decision named above.
