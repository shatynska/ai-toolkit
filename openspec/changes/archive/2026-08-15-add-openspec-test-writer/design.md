## Context

The library ships eight skills and one agent, `openspec-change-reviewer`. That agent is the structural precedent for this one: dispatched against a named OpenSpec change, holding no history of the conversation that produced it, supplied its inputs rather than discovering them, and returning a structured report. See proposal.md for motivation; this document covers how the agent is shaped.

Two facts external to this change determine most of its design. First, `skills/testing` now exists and states the testing floor — so this agent can be an adapter rather than a standard, which is a materially smaller and safer thing to author. Second, a subagent declaring `Skill` in its `tools` grant can see and invoke the library's skills; this was verified empirically rather than assumed, because neither the shipped agent guide nor any of the 34 agents in the official marketplace corpus declares `Skill`, which reads as evidence it does not work when it only shows that nobody uses it.

Where this agent diverges from the reviewer, the divergence is deliberate and recorded, for the reason this repository's previous design documents gave: the precedent is strong enough that a later reader would otherwise read a difference as an oversight.

## Goals / Non-Goals

**Goals:**
- Turn a change's stated behavior into tests before implementation begins, so the tests constrain the code rather than describing it.
- Make coverage of a change's scenarios **countable** rather than a matter of judgment.
- Guarantee the pass is additive — a dispatcher can rely on "this never deletes a test" without auditing the agent's reasoning.
- Keep the agent thin by deferring the testing standard to the skill that owns it.
- Surface `MODIFIED` and `REMOVED` deltas' obsolete tests, which nothing in the current flow looks for.

**Non-Goals:**
- Implementing the change. That is the apply step, and the separation is the point — see Decision 1.
- Deciding whether a change is worth testing on its merits. The only exit is `skip_specs: true`, which is a file read.
- Being a general test-writing agent. It operates on an OpenSpec change; outside that it has no input contract.
- Carrying the testing standard. That is `skills/testing`, invoked (Decision 3).
- Gating task completion on tests passing. Deferred, per proposal.md.
- Choosing or installing a test runner. The dispatch names the command.

## Decisions

**1. A separate execution context is the whole point, so the routing gate passes on an unusual ground.**
`create-agent`'s gate asks whether work needs its own context. For most candidates the answer turns on cost — context size, tool isolation. Here it turns on **epistemics**: the reason to spend a subprocess is precisely that this author has not seen the implementation and cannot pattern-match against it. `skills/testing`'s specified/derived rule narrows the shared-blind-spot problem inside one context but cannot close it, and `add-testing-skill`'s design says so explicitly. A skill cannot supply what is wanted here, because a skill runs in the caller's context by definition — which is the thing being excluded. This is recorded because a later reader seeing a thin agent that mostly invokes a skill would reasonably ask why it is not simply the skill.

**2. It is an adapter over `skills/testing`, not a second copy of the standard.**
Everything the agent knows about what makes a test's evidence interpretable comes from the skill. Its own body carries only what is OpenSpec-specific: the dispatch contract, scenario enumeration, the four delta operations, `skip_specs`, the manifest, and the additive-only boundary. The alternative — inlining the standard so the agent is self-contained — was rejected: two copies of one standard drift, and only one of them is the one anyone maintains. The cost accepted is a runtime dependency on the skill being installed, which holds because both ship in the same plugin.

A second sharpening, for a different reason. *The Testing Standard Is Invoked, Not Restated* and *The Pass Is Additive Only* were drafted to bind the same body text in opposite directions: the first made a rule "about weakening a test" a defect to be replaced by a reference, and the second required the body to state the never-edit prohibition outright. That is the same contradictory-`SHALL` shape this document already repaired for the glob and the manifest, surviving one requirement over — which is worth recording, because fixing the pair that was pointed at is not the same as checking whether the shape recurs. The line drawn: non-restatement reaches the floor's **rationale, classifications and diagnostic procedures**, which are what drift and what the agent can look up at runtime having loaded the skill. It does not reach the agent's **standing prohibitions**, which a dispatcher relies on before any skill has loaded and which therefore have to be readable in the body itself.

The line between deferring and restating needed sharpening after review. Deferring does not mean the agent can inherit a floor obligation it has no way to discharge. `testing`'s project-convention rule directs that an unanswered project question be *asked* — and a dispatched subagent has no channel to ask on, so inheriting it unchanged means skipping a `SHALL` of the skill the agent is built on, or answering from assumption and reporting plausibly. The remedy is neither inlining nor ignoring: it is the **dispatch-shaped translation** of the rule — which conventions arrive by dispatch, and where an unanswerable question goes when there is nobody to ask. That is OpenSpec-specific adaptation, which this decision already licenses, rather than a second copy of the floor.

**3. `Skill` is granted, and the coarseness of that grant is accepted and named.**
`Skill` cannot be scoped to particular skills: an agent holding it can invoke every installed skill, including ones with side effects. The agent's body names which skills it may load, and that is a norm rather than a mechanism — stated plainly rather than presented as a constraint. Two alternatives were considered. Passing the skill's absolute path in the dispatch and reading it with `Read` was rejected as solving a problem that does not exist now that invocation is verified, and it would put the library's own file layout into every dispatch payload. Inlining is Decision 2's rejected option. The residual risk is bounded by the same observation that bounds `Read`: an agent that can read any file is already trusted not to read arbitrarily.

**4. Additive-only is stated as a property, and backed by a dispatch-supplied path glob.**
The strongest version of "never weakens a test" would be a tool grant that cannot write to existing files, and no such grant exists — `Write` is `Write`. So the guarantee is layered: the body states the prohibition as absolute and unconditional, and the dispatch supplies a test-path glob whose violation is a stop-and-report rather than a judgment call. `MODIFIED` and `REMOVED` are where an agent would otherwise have a *legitimate-sounding* reason to edit an existing test, which is exactly the shape of the failure this change exists to prevent; routing them to a list rather than an edit removes the reasoning path entirely. This decision closes the path to *editing* an existing test. It was never a reason to withhold a **new** one, and a later draft read it as though it were: `MODIFIED` was given an obsolete-list outcome and nothing else, which left the operation carrying changed behavior as the only one producing no coverage — the change's own motivating gap, reached through its own rules. Writing a new test for a revised scenario is additive, lands inside the glob, and touches no existing test, so the closure here is unaffected by it. `MODIFIED` therefore produces both outcomes.

The boundary carries exactly one enumerated exception, added after review: the manifest, at `<changeRoot>/test-manifest.md`. An earlier draft stated the glob rule and the manifest rule as unconditional and contradictory `SHALL`s about the same write, which would have had the agent halt on producing its own deliverable — coverage on disk with no record of what covers what. The exception is a single named path rather than a general permission to write where the dispatcher allows, because a boundary with one enumerated hole stays checkable while one admitting a judgment about legitimate locations reintroduces the reasoning this decision removes.

This decision shifts a judgment onto a human, and an earlier draft did not give them the means to exercise it. Routing `MODIFIED` and `REMOVED` to a list rather than an edit keeps the agent additive — but the list is then the input to a *destructive* action someone else performs, and the guarantee stops at the report. An entry made on grounds the reader cannot see does not prevent the loss; it relocates it one step downstream, outside the boundary this decision draws. Three things close that, all inside the existing design: the search is bounded to the dispatched test-path glob (the agent holds `Grep` and `Glob` already, and an unbounded search would be guesswork presented as a finding); every entry records the evidence it was matched on and is marked a candidate for confirmation rather than a conclusion; and finding nothing is stated explicitly, because an empty list reads as "none exists" while usually meaning "none was found". The alternative of dropping the obsolete list was rejected in proposal.md's third motivating gap and stays rejected — the remedy is evidence, not silence.

The cost is real and accepted: a `MODIFIED` requirement leaves the suite red until a human acts. That was chosen over the alternative, which trades a property you can rely on for one you have to audit.

**5. The manifest is a plain file in the change root, not a schema artifact.**
Adding a first-class artifact would need `openspec schema fork`, which produces project-local configuration that cannot ship in this plugin — so every consuming project would repeat the setup. Annotating `tasks.md` instead was rejected on two grounds: the apply phase parses its checkbox format, and it already has two writers (`openspec-propose` creates it, `openspec-update-change` revises it), so a third would risk a later revision silently dropping the annotations. A standalone file has one known cost — `openspec instructions apply` builds `contextFiles` from schema artifacts, so the manifest is not surfaced to whoever implements. The `rules/` fragment closes that, and the agent's report states it too, so the gap is covered twice rather than by a fragment whose import path is machine-local.

**6. The `skip_specs` exit is mechanical, and it is the only exit.**
A mandatory step that can decide it is not needed reproduces the failure this change addresses — an agent under pressure rubber-stamping "no tests required". `openspec validate` rejects a zero-delta change unless `.openspec.yaml` sets `skip_specs: true`, so "this change has no stated behavior to test" is a **file read**. Every other change yields at least one scenario, and a scenario is either covered or listed with a reason. There is no path where the agent concludes on its own that testing was unnecessary.

Two corrections after review. The exemption is read from `.openspec.yaml`, whose path is now an essential input — an earlier draft called the exit "a file read" while supplying no path to the file and forbidding path construction, so the read had nowhere to start. And absent delta specs plus the marker now routes explicitly to the exempt report rather than to blocked-and-stop: without that, an exempt change tripped the missing-essential-input rule and returned `blocked`, indistinguishable from a malformed dispatch, and the exit this decision calls the only one never fired.

**7. Tools: `Read, Grep, Glob, Write, Bash, Skill`; the write grant is what makes this expensive to get wrong.**
`Read`/`Grep`/`Glob` for artifacts and existing tests; `Write` for tests and the manifest; `Bash` to run the suite for the baseline and to observe the new tests fail; `Skill` per Decision 3. This is a wider grant than `openspec-change-reviewer`'s `Read, Grep, Glob`, and the difference is the whole risk surface: the reviewer is read-only **by grant**, and this agent is additive-only **by promise**. That asymmetry is stated rather than smoothed over, because it changes how much the body's wording has to carry.

**8. The cold-run check runs in an isolated worktree, and the worktree is not a sandbox.**
`agent-authoring` requires isolation for a write-capable agent: create a worktree, copy the uncommitted definition into it (a worktree from a committed ref does not contain it), rewrite every writable payload path to the worktree root, and launch from there. All of that applies. The standard also requires stating what isolation does not cover — this agent holds `Bash`, which can address any path the process can reach, so the payload and the run's permission mode are reviewed before the run rather than treated as contained. Recorded as a decision rather than left to tasks, because the natural reading of "isolated" is stronger than what a worktree delivers.

**9. Name `openspec-test-writer`; tags `testing` and `openspec`; no new tag.**
The name states the flow it belongs to and the work it does, matching `openspec-change-reviewer`'s shape. Both tags exist already — `testing` from `skills/testing`, `openspec` from the reviewer — so `toolkit-structure`'s check passes with nothing coined. `test-author` and `spec-test-writer` were considered; the first loses the flow, the second reads as authoring a spec.

**10. The description carries the dispatch contract, following the reviewer rather than diverging from it.**
`change-review` requires that agent's `description` to name the inputs a dispatch must supply, on the reasoning that the body loads only after the payload is fixed, so a contract stated only in the body is read by the agent and never by what feeds it. An earlier draft of this change did not carry that requirement across, and the omission was not recorded as a divergence — which this document's Context says divergences must be. On examination the precedent applies with *more* force here, not less: this contract has more inputs, and two of them (the test command, the test-path glob) cannot be derived from the change at all, so a dispatcher working from an incomplete description produces a well-motivated dispatch that blocks. Following the precedent was chosen over justifying a divergence from it, because no justification survived the comparison.

**11. The set-change invalidation rule is read as not reaching a library addition — recorded because two reviewers have read it oppositely.**
`agent-authoring` states two invalidation rules: adding an asset invalidates the recorded checks of assets it *competes with*, and a change to the **set** the evaluator holds invalidates *every* check run against the previous composition. A review of this change read the second as covering this addition, which would require re-running every recorded check in the library. This change does not adopt that reading, and the reason is a **specific rule governing a general one**, not an inference from the clause's phrasing. `skill-authoring`'s addition rule carries the scenario *Unrelated assets are not re-checked*: an asset competing with no existing recorded prompt triggers no re-run. Under a library-wide reading of the set-change clause that scenario is dead letter, since every addition would re-run everything. A reading that leaves a stated scenario with nothing to govern loses to one that does not.

An earlier draft of this decision argued instead from the clause's own wording — that a sentence disclaiming the library-addition rule's coverage of *widening* implies additions fall under that other rule. That is a converse inference and does not carry on its own; it is recorded as superseded rather than deleted, so the weaker argument is not reconstructed later and mistaken for the reasoning.

Two independent reviews have now reached this same conclusion — one on `add-testing-skill`'s identically-worded `skill-authoring` clause, one on this change — against one that read it the other way. That the text supports opposite readings at all is itself a finding: the text is ambiguous enough to support both, and a clarifying edit to `agent-authoring` and `skill-authoring` is worth making. That edit is **not** in this change's scope — it would modify two capabilities this change otherwise leaves untouched, on a question that does not block this agent — and is recorded here so it is proposed separately rather than forgotten.

**12. `effort` is not declared, deliberately.**
The frontmatter contract admits it; this agent does not declare it, so it inherits whatever the dispatcher runs at. The work is bounded by the change's size rather than open-ended, and a declared effort would fix a cost the dispatcher is better placed to judge. Recorded because an earlier draft simply never mentioned the field, which reads as an oversight rather than a decision.

**13. What yields if the description cannot carry everything required of it.**
The description must name seven essential inputs plus `specsRoot` as conditionally essential and an optional prior-manifest path, summarise two to four dispatch scenarios, state the moment, the additive property and the output type, disambiguate against two assets, and point at `## When to invoke` — against a length limit. `add-testing-skill` overran that limit on its first draft by thirty percent, so this is a live constraint rather than a theoretical one, and a `SHALL` with no stated precedence is improvised against under pressure. The order: the **essential inputs** yield last and are carried as a terse comma-separated list rather than prose, because a dispatcher that cannot name them produces a blocked dispatch and the description is the only surface it reads; the **scenario prose** yields first, down to the two-scenario floor, because `## When to invoke` carries the worked detail anyway; disambiguation yields next, to the single most confusable asset. If it still does not fit, that is a signal the contract is too large rather than the description too small, and it returns here rather than being trimmed further.

**14. What the agent may read is bounded, because ordering alone does not secure Decision 1's ground.**
Decision 1 passes the routing gate on the claim that this author has not seen the implementation. For an `ADDED` requirement dispatch ordering delivers that for free — the code does not exist yet. For a `MODIFIED` one it does not: the pre-change implementation is present, and the obsolete search is an invitation to read it. An earlier draft left the property the whole agent is justified by stated by no requirement, so a body could satisfy everything else here while deriving assertions from the code it exists to constrain. The bound adopted is a read allowlist — change artifacts, `specsRoot`, dispatched convention files, a supplied prior manifest, and the test-path glob — with the specification comparison, not the code, as the means of establishing what a `MODIFIED` delta supersedes. The alternative considered was to rely on Decision 2's specified/derived provenance rule, which does constrain what an assertion may claim; it was rejected as insufficient here, because provenance governs where an assertion's *authority* comes from and says nothing about what the author may look at while choosing it. Like the additive-only guarantee this is held by prose rather than by grant — `Read` is `Read` — and Decision 7's asymmetry applies to it identically.

## Risks / Trade-offs

- **Additive-only leaves the suite red after a `MODIFIED` requirement.** Nothing in this change fixes the obsolete tests; a human does. → *Mitigation*: accepted deliberately per Decision 4. The manifest names each obsolete test and the delta superseding it, so the work is enumerated rather than discovered.
- **"Never write implementation" is a promise held by a body, not by a grant.** The likeliest breach is at the moment tests fail because the target is absent, where creating a stub presents itself as repairing the tests. → *Mitigation*: `skills/testing` names that exact drift point and the agent inherits it; the body restates the prohibition as an OpenSpec-flow rule; the path glob makes a write outside test paths a stop condition.
- **The agent is thin only while `skills/testing` says what it says.** A change to that skill silently changes this agent's behavior. → *Mitigation*: named in proposal.md's Impact so a future edit to `testing` considers this agent's fixtures. Not closed — this is the cost of Decision 2, taken knowingly over drift.
- **Trigger competition with `openspec-change-reviewer` is the closest this library has come to two assets on one dispatch.** Both act on a named change at adjacent moments. → *Mitigation*: the descriptions state the moment and the output — one reviews a plan and returns a verdict, the other writes tests and returns a manifest — and both sets of fixtures are re-run in this change.
- **The agent now depends on more dispatch inputs than any asset in this library.** Seven unconditional essential inputs, one conditional (`specsRoot`) and one optional (a prior manifest path), against the reviewer's three-plus-two. Every one is a way for a dispatch to be incomplete. → *Mitigation*: Decision 10 puts the contract in the description where a dispatcher reads it before assembling a payload, and the blocked report names precisely what is missing rather than failing generically. The count is a consequence of the work — a test author needs the project's runner, its test layout, and its conventions, none of which the change itself carries.
- **A scenario is not always one test, and the countable check can read as if it were.** A single WHEN/THEN may need several tests, or one test may satisfy several scenarios. → *Mitigation*: the requirement is that each scenario be *accounted for*, not that the counts match one-to-one; the manifest maps many-to-many.
