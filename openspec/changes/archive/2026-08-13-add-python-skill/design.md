## Context

The library ships four skills (`bash`, `create-agent`, `create-skill`, `langgraph`, `terraform`, `n8n-workflow-review`) and one agent (`openspec-change-reviewer`). `bash`, `terraform`, and `langgraph` are the domain-asset precedents: general floors that state authoring discipline for a language or tool, deferring to a consuming project's own conventions on conflict. See proposal.md for the motivation and scope; this document covers how the skill is shaped.

`bash` is the closer structural precedent for scope discipline (general-purpose, not shaped by the motivating project's domain) and for the traps-first body over tutorial content. `langgraph` is the closer structural precedent for size and structure: it is the only existing domain skill that pre-split into `SKILL.md` plus `references/` because the domain surface was wide enough at the wanted depth, rather than growing into a split later the way `bash`/`terraform` explicitly left as an unused escape hatch. This change follows `langgraph`'s precedent on structure and `bash`'s precedent on scope discipline, for a reason specific to Python: it is a general-purpose language, not a bounded artifact like a shell script or a `.tf` file, so its floor-level trap surface is wider than either `bash` or `terraform` covers even before any project-specific depth is added.

Where this change diverges from either precedent, the divergence is deliberate and recorded below, for the same reason `add-bash-skill`'s and `add-langgraph-skill`'s design docs gave: the precedent is strong enough that a later reader would otherwise read a difference as an oversight.

## Goals / Non-Goals

**Goals:**
- Ship Python guidance that changes agent behavior rather than restating what a competent model already supplies about the language's basic shape (syntax, literals, how to define a function or class).
- Concentrate content on behaviors where a reasonable reading of Python code still yields the wrong answer — a shared mutable default argument, a closure that captures the loop variable rather than its value, an `is` comparison that appears to work by cached-integer accident, an exception silently discarded by a broad `except` or a `return` in `finally`.
- Hold version-dependent claims (CPython small-int/string interning range, `ruff`/`mypy` default rule coverage) to a live-verification standard, matching `bash`'s ShellCheck verification and `langgraph`'s API verification.
- Compose with a consuming project's own conventions rather than competing with them, matching `bash-practice`, `terraform-practice`, and `langgraph-practice`.
- Stay general-purpose across project shapes even though a concrete new project motivates the change now, matching `bash`'s rejection of `infra-bash` and `langgraph`'s rejection of `langgraph-multi-agent`.

**Non-Goals:**
- Teaching Python to a human. A skill loads into an agent's context; it is not documentation the user reads. Same non-goal `bash`, `terraform`, and `langgraph` carry.
- A style guide (PEP 8 formatting, naming conventions, docstring format). None of that changes behavior, and `ruff`'s formatter/style rules already cover the mechanical parts a project would want enforced — this skill covers behavior that reads as correct and isn't, not house style.
- Scoping to any one project shape (web backend, data/ML pipeline, CLI, service) — see Decision 3.
- A full concurrency, packaging, or typing curriculum. These get a `references/` file each at floor-relevant depth (the traps, not a tutorial on `asyncio` or `pip`), not comprehensive treatment.
- A project's own dependency-management tool choice (`pip`, `poetry`, `uv`, etc.), packaging layout, or style conventions beyond the core traps, which belong in that project's `AGENTS.md`.
- Python 2 compatibility or porting concerns. The skill assumes Python 3.

## Decisions

**1. Pre-split structure from the outset, diverging from `bash`/`terraform`'s flat-file precedent and following `langgraph`'s.**
`bash` and `terraform` both project comfortably under the ~5,000-word single-file budget and treat `references/` as an unused escape hatch. `langgraph` pre-split because its domain surface — fourteen distinct topics at the depth wanted — didn't fit that budget at the outset. General Python's floor-level trap surface (mutability/aliasing, scoping/closures, identity/equality, exception handling, iterator/generator semantics) is itself comparable in breadth to `bash`'s ten sections before any deeper material is added, and the deeper material this change wants (concurrency, imports/module-state, typing/tooling, datetime/numerics) would push a flat file well past a single readable pass. Pre-splitting, rather than waiting to discover this at Draft the way `bash`/`terraform` were entitled to, was chosen because the shape is already evident from the trap inventory in proposal.md — the same reasoning `langgraph`'s design used, applied earlier because the evidence is already in hand rather than needing a drafted flat file to surface it.

**2. `references/typing-and-tooling.md` carries the `ruff`/`mypy` necessary-but-not-sufficient discipline, mirroring `bash`'s ShellCheck mechanism.**
`bash-practice`'s strongest completion mechanism is ShellCheck: required, but explicitly insufficient, with the skill stating what a default run misses. Python has an equivalent lever, and live verification against `ruff` 0.16.3 (task 3.2 of this change) found its zero-config default rule set broader than the "E4/E7/E9/F only" reputation this decision was initially drafted against: it already catches a mutable default argument (B006), a mutable class attribute default (RUF012), `is` used to compare a literal (F632), a late-binding closure in a loop (B023), a `return` inside `finally` masking an exception (B012), and a bare/broad `except` (BLE001/S110) — all by default, no config needed. What it structurally misses: aliasing vs. copying (mutating a list through a second reference is ordinary, valid-looking code, not a pattern an AST match can flag as wrong), mutating a list while iterating over it, generator single-use exhaustion, `__exit__` swallowing an exception on a truthy return, and general float-equality comparison outside the specific `float("nan")`-literal pattern its `PLW0177` rule matches. `mypy` contributes little beyond ruff for this trap set — it is a type checker, and none of these traps are type errors. Stating the corrected split explicitly — which traps are caught, which aren't, and that a clean run therefore isn't sufficient — was chosen over either omitting a tooling requirement (which would give up a mechanism `bash-practice` shows is valuable) or treating a clean run as sufficient (which would silently drop the traps a linter can't see, the same mistake `bash-practice`'s design rejected for ShellCheck).

**3. Scope stays general-purpose across project shapes; the motivating project informs no section's depth.**
Both `bash` and `langgraph` had a concrete motivating project and both design docs record the same conclusion: the traps hold regardless of the project's shape, so narrowing to the motivating shape would forgo other audiences at no benefit to the motivating one. This change's user explicitly declined to let the new project's shape (web/data/CLI/service) drive which section gets developed in depth, which settles by direct instruction what `bash` and `langgraph` settled by design-doc argument: no section of the floor or the `references/` set is scoped to, or weighted toward, one project shape. The `references/concurrency.md`, `imports-and-state.md`, `typing-and-tooling.md`, and `datetime-and-numerics.md` split is therefore drawn from general Python-floor coverage, not from an inferred project profile.

**4. `langgraph` gets a cross-reference, not an exclusion boundary.**
Both skills are Python and both could plausibly trigger on a prompt like "review my Python file" when that file happens to be a LangGraph graph. The alternative to a cross-reference — an exclusion clause stating that `python` does not apply to LangGraph code — was rejected: `python-practice`'s core traps (mutable defaults, late-binding closures, broad `except`, and the rest) apply to LangGraph code exactly as they apply to any other Python code, so excluding LangGraph code from the floor would be wrong, not just imprecise. The correct division is by *topic*, not by *file*: LangGraph-specific material (state/reducers, conditional-edge routing, checkpointers, multi-agent handoff) stays owned by `langgraph`, and everything else in a LangGraph file is still owned by `python`'s floor — the same shape `bash` uses for its relationship with `terraform` (shell-side semantics vs. provisioning semantics, both potentially in play on the same script).

**5. Version-dependent claims verified live, or explicitly sourced from documentation when a live check isn't possible.**
Two claim classes in this skill are version-dependent in a way that can silently date: CPython's small-integer/string interning range (implementation-defined behavior, not language-guaranteed, and could in principle change between CPython versions) and `ruff`/`mypy`'s default rule coverage for the traps this skill names as caught vs. missed (a linter's default rule set changes across releases). Both are held to the same live-verification discipline `bash` applied to ShellCheck and `langgraph` applied to its API surface, with the verified version recorded in the authoring record — so staleness is detectable rather than silent, matching the residual-risk acceptance both precedents already made.

**6. Name `python`; one new tag `python`; no `allowed-tools`.**
The bare language name is what a user types and matches the `bash`/`terraform`/`langgraph` precedent of naming the skill after its subject rather than a paraphrase (`python-best-practices`, `python-authoring` were both considered and rejected on the same grounds those precedents already established). No `allowed-tools`: this is open-ended authoring guidance across an entire language, not a wrapper around one external command.

## Risks / Trade-offs

- **"General Python" is a far larger domain than shell or a single `.tf`/`langgraph` surface, so the floor risks either drifting into style-guide territory or staying too thin to be useful.** → *Mitigation*: the core-traps requirement fixes a minimum list selected by the same "contradicts a reasonable reading of the code" bar `bash` and `langgraph` used, and the Non-Goals section explicitly excludes style/formatting as `ruff`'s formatter territory, not this skill's.
- **The pre-split-from-the-outset structure (Decision 1) hasn't been validated against a drafted flat file the way `langgraph`'s split was discovered at Draft.** The projection could be wrong in either direction — the floor could still fit flat, or a `references/` file could turn out too thin to justify its own file. → *Mitigation*: carried as an explicit tasks.md checkpoint (draft the outline, check actual word counts, and collapse a reference file into the floor or merge two reference files if either turns out too thin), rather than treated as settled by this document alone.
- **Trigger competition with `langgraph` is the most concrete risk this library has faced yet**, since both are Python and both are general-purpose within their scope. → *Mitigation*: Decision 4's topic-based (not file-based) division, stated in both skills' descriptions, and `langgraph`'s recorded trigger-check fixtures are re-run as part of this change per proposal.md's Impact section.
- **CPython's small-integer/string interning behavior is implementation-defined, not a language guarantee**, so a claim verified against the current CPython version could describe behavior another Python implementation (PyPy, etc.) doesn't share. → *Mitigation*: the skill states this is CPython-specific interning behavior rather than a language guarantee, so the trap is framed correctly (don't rely on `is` for value comparison at all) rather than as a version-specific fact that could mislead on a different implementation.
- **The `ruff`/`mypy` caught-vs-missed claims in `references/typing-and-tooling.md` are the kind of granular, version-sensitive detail most likely to date poorly.** → *Mitigation*: same residual risk `bash-practice` accepts for ShellCheck's version-dependent behavior; Decision 5's verified-version record makes staleness detectable rather than silent.

## Harvest candidates

Recorded per the close-out task, for a future edit to `skills/python/` rather than added to this change — none is load-bearing for the delta spec's minimum content, and adding any now would be padding beyond what the spec requires.

- **`dataclasses` reject a mutable default field outright, at class-definition time, rather than sharing it silently.** Verified live during authoring: `@dataclass class C: items: list = []` raises `ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory` the moment the class body executes — a loud, immediate failure, unlike the plain-function mutable-default-argument trap this skill covers, which is silent and only surfaces on the second call that hits the shared object. `field(default_factory=list)` is the correct replacement, confirmed working live. Not included in the shipped `SKILL.md` because the spec's minimum trap list is function/class-attribute defaults, not the `dataclasses` module specifically — worth adding as a "and here's the loud version" contrast if a future edit wants to round out the mutability section.
- **`unittest.mock.patch` must target the name as looked up in the module under test, not where the patched object is defined** — the classic "patch where it's used" rule. Not verified live or included here because this skill's shipped scope has no testing section at all (the trap list is authoring traps, not testing-specific ones); worth adding as a `references/testing.md` file if a future edit wants to extend the skill into test-writing practice, which this change deliberately did not scope into.
- **`contextlib.suppress` is the correct, explicit way to intentionally swallow a specific exception**, in contrast to `SKILL.md`'s `__exit__`-returning-`True` trap, which is about *accidental*, undocumented suppression via a hand-written context manager. Not included because the shipped section is about the trap, not about the tool that does the same thing on purpose — worth a one-line contrast if a future edit wants to give the trap a clearly-marked "here's how to do this deliberately instead" pointer, matching how `bash-practice`'s traps sometimes pair a footgun with its safe alternative.
